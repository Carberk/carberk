# Admin application

The internal web app provides moderation, content-report review, inspection-interest statistics, audit access, and brand logo management. The shared TK/RU/EN root locale provider preserves current forms and filters while switching language. `/workspace` reads current staff capabilities and a separate actual marketplace-admin check for navigation. Scoped routes include `/services`, `/diagnostics`, `/improvement` and `/operations`; their owning APIs enforce current capabilities and assignments independently of navigation. A workspace panel without a route remains unavailable. Existing moderation routes retain their server/API guards. Broader dashboard capability belongs to the product specification, not this overview.

`/listings` and `/users` expose bounded read-only marketplace context through Admin-owned projections. Global directories and direct reads require a current marketplace-admin role and current-session TOTP at the API; `support.operations` alone grants neither a directory nor arbitrary User lookup. Contact/sign-in fields and private Conversation, payment, staff-grant and report artifacts are excluded. Listing photos use released photo variants. Tester-gated video upload, processing, protected media grants and lifecycle erasure are implemented with flags closed by default. Seller editing and buyer poster/player surfaces are still being integrated; native acceptance and rollout activation remain pending. Existing moderation actions remain separate and retain their own write safeguards.

Browser JavaScript never receives API tokens. Server-side code stores them in HTTP-only cookies and forwards bearer authentication to the API. Preserve production `__Host-` cookie restrictions, origin validation on browser-posted handlers, and local-only `returnTo` validation. The Node `src/proxy.ts` renews expired requests before rendering or Server Actions, forwarding the rotated cookies to the handler and storing both on the response. Layout/API checks still enforce actual authentication and TOTP elevation. Server Components never rotate tokens or write cookies.

`API_BASE_URL` accepts an http(s) origin or an address ending in `/api/v1`, with an optional trailing slash. Production requires it and validates it at server initialization, before accepting requests. Development retains the public-URL/local fallback. The network regression in `apps/api/src/modules/identity/presentation/AdminApiBridge.spec.ts` uses the real admin client and running API OTP controller; it does not replace `fetch`.

Sign-in creates an ordinary session. Admin and scoped staff access additionally need personal TOTP elevation. The scoped sign-in bridge checks current server eligibility rather than treating marketplace role as a private capability. Pending enrollment reuses the same secret until verification; refresh does not extend the elevation deadline. Logout clears local cookies even if API revocation fails. Keep token and credential values out of logs and errors.

The Brands page (`/catalog/brands`) lists every brand with its logo or a letter fallback and uploads, replaces, or removes a logo through server actions. The browser sends the file to the server action, which checks type and size, asks the API for a presigned PUT, uploads the file to storage from the server, and confirms the key with the API; the API owns the full validation.

The reports queue labels and filters Message reports in the current admin locale. Detail shows only the reported Message, its attachment marker and sender, links to that sender's User page, and permits suspension or dismissal. Deleted Messages and senders stay readable; unavailable or already suspended senders have no suspension action. Staff content access is audited by the API.

Admin must run as exactly **one process and one Railway replica** for the first release (one or two operators), until a shared session store exists; see [ADR-0090](../../docs/adr/0090-single-process-admin-session-renewal-for-the-first-release.md) and [#746](https://github.com/bagtyyarkovusov/auto.tm-rewrite/issues/746). The process-local renewal owner shares one rotation per SHA-256 hash of the old refresh token. Successful pairs remain only in memory for five seconds, with at most 128 pending or completed entries; token values are never logged. Only missing refresh or API 400/401 rejection clears both cookies and returns to login. Cache capacity, timeouts, network failures and API 429/5xx retain cookies and require retry. One pending rotation serializes admission; random unvalidated cookies cannot fill the handoff cache. Restarts or a second process may expose a spent token to API rejection. An old token replay within the five-second handoff receives the cached pair without reaching API reuse detection; ADR-0090 records this accepted cost. A session-expired URL alone cannot clear a healthy session. An expired Server Action renews first and runs once on success. On failed renewal, the proxy clears cookies and marks the request; every action starts with `rejectExpiredSession`, which uses Next’s native action redirect before validation or API work. Ordinary POSTs receive a 303 to login. No failed mutation executes or automatically replays. API lifetimes, reuse detection and TOTP elevation deadlines remain unchanged.

Tests beside the API client, cookies, validators, and server actions cover these boundaries. `/healthz` remains independent of the API and data stores.

`/business-admission` is a bounded admission/recovery feature outside the legacy marketplace-admin-only layout. Its server read and actions require the current elevated `founder.admission`/`founder.recovery` capability, with final transaction authority in Identity. It supports TK/RU/EN, defaults disposable admission to synthetic, and prepares a recipient-bound single-use owner invitation without sending messages. It consumes the shared staff navigation and locale provider, preserving unfinished admission evidence across locale changes.

`/operations` releases only the strict, fresh health snapshot permitted by `analytics.aggregate`, clears denied or expired data and labels absent billing/recovery evidence as unavailable. It does not provision monitoring or authorize deployment. `/services` uses current private-service authority for queues, Support and history fulfilment; its proxy never redirects the browser to a raw private storage URL. Synthetic service actions do not establish live payment/provider readiness.

The `/diagnostics` staff workspace composes finite classified identity evidence, explicit predecessor comparison, exact reviewer-to-technician handoff navigation and same-Session request recovery through existing protected actions. Handoff navigation performs B-owned reads only and grants no authority. Automatic ownership/first-capture admission remains closed; native copy review, rendered accessibility and integrated journey acceptance are separate outstanding gates. Start with [continuity composition](src/app/diagnostics/DiagnosticContinuity.tsx), [identity capture](src/app/diagnostics/DiagnosticIdentity.tsx) and their transport-boundary component tests.
