# Mobile listings

This area contains create-wizard state, draft persistence, upload staging, edit-save orchestration, discovery state, and listing presentation. The create route and edit route have different orchestration; inspect both before consolidating shared UI. Server lifecycle and contact rules belong to [API Listings](../../../api/src/modules/listings/CONTEXT.md).

## Important constraints

Create flow uses the wizard machine and autosave; edit flow computes and sequences changes against an existing listing. `useSaveListingEdit` runs the sequential best-effort save of [ADR-0025](../../../../docs/adr/0025-edit-save-atomicity.md): it fixes an edit plan when Save starts and keeps a session ledger of the server media IDs attach returned and the media it removed. Reorder, retry and a repeated Save use those server IDs, never a photo's local staging ID, and neither a refetched Listing nor a retry attaches or removes the same photo twice. Retry replays the fixed plan only while the fields and photos are unchanged; edits made after a failure re-plan from the ledger like a fresh Save. Save and Retry return whether they ran, and one runs at a time. Shared contract schemas own validation. Do not make the UI's visual step number a second validation model. Photo UI receives its actual props from the live component interface; old Step2Photos warnings and historical refactor plans are not current requirements.

The Sell wizard has seven steps in the order of `WizardSchemas.WIZARD_STEPS` (founder decision D2 on #354). The step name is the identifier that the mobile machine, `validate-step` and draft saving share; titles come from `wizardSteps.<name>` in the i18n resources. Component file names keep their eight-step numbers, so do not read a position from them.

| # | Step name | Title | Component | Fields |
|---|---|---|---|---|
| 1 | `vehicle` | Car | `Step3VehicleId` with `VinField` | Brand, Model, Generation, Year, then optional VIN (17 characters at most, no Skip, no auto-fill) |
| 2 | `specs` | Details and condition | `Step4Specs` | Condition, Mileage, Damaged / needs repair, Known issues, optional specs |
| 3 | `photos` | Photos | `Step2Photos` | 1 to 20 photos |
| 4 | `price` | Price | `Step5Price` | Amount, currency, Exchange, Installment |
| 5 | `location` | Description and place | `Step6Location` with `DescriptionField` | Description (required, up to 2000), then Region, City, Area |
| 6 | `contact` | Contact | `Step7DescContact` | Contact phone (today's free text), calls and chat switches (at least one on) |
| 7 | `review` | Check and publish | `Step8Review` | Sections in the same order, each with Edit |

Each step depends on all earlier ones, and a changed field invalidates its owning step and every later step (`getInvalidatedSteps`; `vin` belongs to `vehicle`, `description` to `location`). The header reads "Step N of 7" and announces the step title with that position when a step opens. Edit uses the same seven steps and locks the whole Car step, VIN included.

Resume derives completion from the saved fields, never from stored step names. On `INIT` the machine runs every data step's schema against the payload; a create draft opens at the first incomplete step, or at Check and publish when all six pass. A draft saved by the eight-step wizard (names `vin, photos, vehicle, specs, price, location, contact`, VIN first, description on Contact) therefore lands on the right step, and its VIN stays in the payload under Car. The API's draft saving drops step names that no longer exist. The payload's `currentStep` is still written as 1 and not read; remembering the step the seller left belongs to a later slice.

Publishing depends on required fields, contact verification, and successful media attachment. A file appearing in a preview does not prove it was uploaded or attached. Preserve retry state and draft reconstruction, and inspect the queue, publish-gate code, and tests when changing navigation or autosave timing.

The condition disclosure is one required Yes/No question, **Damaged / needs repair**, plus optional **Known issues** ([ADR-0052](../../../../docs/adr/0052-seller-condition-disclosure-is-damaged-plus-known-issues.md)). For a Used car, the Details and condition step leaves it unanswered until the seller picks one, and the shared `StepSpecsSchema` blocks the step (`wizardErrors.damagedRequired`) until then. For a New car the question is hidden and the draft stores `damaged: false`; switching New to Used clears that answer and asks again, and a damaged New draft shows `wizardErrors.damagedNotForNew` under Condition ([ADR-0080](../../../../docs/adr/0080-a-new-car-skips-the-damaged-question.md)). A legacy Used Listing without an answer enters edit at the specs question before the seller can save; a New one enters at review. Sell and Edit keep Mileage, Engine power and disclosure errors quiet until that field is touched or the specs step is attempted; changing New to Used starts with untouched, unanswered Used questions. Specs Continue/Done accepts an invalid-field attempt, reveals the errors, and stays on the step; other invalid-step controls stay disabled. Pending operations still block the footer. Create-wizard load derives `damaged: false` only for a missing New answer, preserving explicit `true` for rejection. A submitted disclosure replaces Known issues, so clearing the input removes the saved text. Listing detail shows it under "Condition, as stated by the seller" and renders nothing when a Listing has no answer.

Listing detail follows the approved Auto.ru content order with AutoTM tokens: photos and numeric counter, title, price, date/city, six key specifications followed by rows, expandable seller description, seller-stated condition, Seller card, Report, and public-number/date footer. Between the description and the seller's condition statement sits Ask the seller. The route owns the sticky Call/Message or owner Edit/Mark sold bar, measured gallery scroll threshold, header actions and Report sign-in/replay. The owner menu holds Archive and Delete, plus Republish for archived Listings. Listing detail hides both Share and Copy link until a public web Listing page and App Links exist (#495, decided in #322); the buyer overflow holds only Report on active Listings, and its trigger is hidden whenever Report is unavailable (sold/archived, or reporting disabled) so no empty menu opens. Views and saves appear only in the owner status card. Sold/archived buyers retain the banner, muted price and similar brand/model link, with contact, Favorite and Report hidden. A 404 offers Home and Back.

Tapping a gallery photo opens `PhotoViewer`: a black full-screen Modal with an `n / N` counter, ✕, swipe paging, a thumbnail strip, and ♡ plus Call + Message. `PhotoGallery` takes the ♡ and the contact bar as render props, so the gallery itself knows nothing about auth; `ListingDetailView` supplies `ViewerFavorite` and a second `ContactCtaBar` (`variant="viewer"`, `replayAuth={false}` so a Message replayed after sign-in opens one Conversation, not two), and supplies neither to the owner or on a sold or archived Listing. A React Native Modal sits above the navigation stack and would hide the sign-in screen, so every viewer action that leaves the screen closes the viewer first (the slots receive `close`). Closing, by ✕ or the system back gesture, hands the photo the viewer was left on to the gallery, which scrolls there. `ZoomableImage` does pinch, drag-while-zoomed and double-tap with Gesture Handler and Reanimated shared values (`zoomMath` holds the clamps), reports only zoomed or fitted to React, and the viewer locks paging while a photo is zoomed. The Modal wraps its content in `GestureHandlerRootView`, as Gesture Handler requires on Android. These gestures run on the UI thread, so the Vitest adapter mocks them and only a device proves them; swipe-down to close, shown as a hint in the prototype, is not implemented.

Listing detail opens instantly from the tapped card. `useListingPreview` reads the card's `ListingSummary` by Listing ID from the feed and Results lists (`queryKeys.listings.lists()`, whatever the filters or viewer), Favorites and My listings caches, and `ListingPreview` shows its photo (the `list` variant the card already decoded), title, price, spec line (`km · gearbox · fuel`), date and city, with the rest behind skeletons and Call and Message disabled until the detail query returns. It is a separate value, not `initialData` or `placeholderData` on the detail query: a summary lacks contact, description and seller, and must never pass for a loaded Listing. The owner and closed Listings get no bar while loading, from the summary's seller and status. A deep link, or a card the cache has evicted, finds nothing and shows the plain `DetailSkeleton`.

Ask the seller (`AskSellerChips`) offers the four QuickReplies intents as chips. A tap opens the Conversation through `useOpenListingConversation` (shared with the Message button) and passes the question as a `draft` route param; the Conversation seeds `MessageComposer` with it through `initialText`, and the buyer still presses Send. Signed out, the chosen intent is parked as `{ kind: "ask", intent }` behind `requireSignIn` and finished on return, resolved to text in the current locale. The chips are hidden for the owner, for sold and archived Listings, and when the seller turned chat off, as Message is disabled then. The four intents are fixed in `QuickReplies`; this feature adds none.

The Seller card uses the real display name or Private seller, join month, and city/place. It has no Phone verified badge; Call carries the SMS-verification caption under ADR-0056. VIN remains a specification row when present; the decoding section renders only for `vinHistory.decoded === true`, with no empty state under ADR-0053. ADR-0057 keeps the inspection component, hook and tests unused: detail no longer renders its entry or reads the inspection config, and publishing no longer requests its sheet. The API endpoint and decoder code remain unchanged.

Picker URIs are copied into persistent temporary storage before parallel compression because iOS may reclaim picker cache files under memory pressure. The compressor copies its result into staging, verifies the destination, and cleans temporary files best-effort. Preserve copy rather than cross-directory move; earlier iOS failures motivated that choice. Overlapping compression/upload operations use reference counters, since a boolean can clear while another operation is still active.

The compressor currently uses the contextual ImageManipulator chain. Consult current Expo docs before an SDK change; historical API notes cannot establish present library support. Staging cleanup is local-device cleanup, distinct from the worker's broad orphan-cleanup queue.

Search/filter UI separates editing state from applied query state. Check the stores, serializers, query keys, and API ranking adapter together when changing filters or result counts. Approved discovery requirements are in the Search specification, not old planned-refactor notes.

Home (`app/(tabs)/(search)/index.tsx`) is the root of the Search tab's own stack, anchored at `index` so a deep link still has Home underneath. `AutoTmTabBar` always emits `tabPress` and navigates only to an unfocused tab, so re-tapping Search pops to Home while other tabs keep their history. Home has no filters: a Brand/model card with the live count and a two-column New listings grid of `ListingGridCard`. Search renders Recent and Popular before typing, then combined brand/model catalog matches. The debounced catalog API owns spelling and year parsing; Search passes its year bounds into Results as `yearMin`/`yearMax` route params. A bare year opens the full feed with that year range, while an unmatched name with a year stays no match. Settling and placeholder results cannot be selected. Search keeps its input editable through loading, errors and offline-paused queries, retries after connection recovery, and opens the keyboard on entry. Back dismisses the keyboard and goes back to the Home underneath through `useSafeBack` (Home is only the fallback when there is no history), so Search never stacks a second Home; a pick replaces Search with Results, so Back from Results returns to Home. All filters replaces Search with Search parameters over Home. Results keeps applied filters and one of the six approved sort orders in route search params, so deep links and Back restore the same search. Its header reads the live matching count and TMT range. Condition and removable city/price/year chips commit in place, with the chips floating at the bottom once the header scrolls away. A single brand/model card shows the chosen brand's `CarBrandLogo` (its letter when there is no logo; the generic car only when no brand is chosen), opens the current ticked models and can clear the selection. "Reset filters" on a no-match Results clears the filters but keeps the current sort. The list stays mounted behind Listing and sign-in navigation, preserving its native scroll position. Results uses `ListingLargeCard`: a photo area that follows the Listing's photos (none gives one "No photos" frame, one gives a single wide photo, two or more give a 62%/38% two-photo grid; the 📷 count shows only above one photo), TMT price, available mileage/gearbox/fuel names, one-line brand/model/year, city/date, and a bottom-right favorite action, plus a skeleton with one wide photo block. A signed-out ♡ on a card stores a pending Favorite; `useFeedFavoriteReplay` finishes it at screen level when the owning Home or Results screen regains focus, because the tapped card may no longer be mounted. Feed cards and Listing detail share `useListingFavorite`. `setFeedFavorited` writes a ♡ state only into signed-in cached feed pages, because a silent sign-out keeps the query cache and Home would otherwise show the previous User's ♥.

Favorites (`app/(tabs)/favorites.tsx`) uses the same `ListingLargeCard` with `isOwn` and `onRemoveFavorite`: Call opens the dialer with the Listing contact phone when the seller allows calls and gave one, Message opens the Conversation through `useOpenListingConversation` when chat is on (a failure shows `ErrorState` under the buttons), neither shows on the User's own Listing, and the filled ♥ removes the Favorite. Sold and archived Listings are dimmed and labelled Sold or Removed from sale, with a muted price and no contact buttons; the card still opens Listing detail. `useFavoritesView` owns what the tab shows. Hide sold (`HideSoldToggle`, one row with the `switch` role) starts on and lives in an in-memory zustand store, so it survives tab changes while the app runs but is never stored on the device. Its position picks the `useMyFavorites({ activeOnly })` list, keyed separately per position (`queryKeys.favorites.list(activeOnly)`, prefix `lists()`), and every page carries `counts` over all visible Favorites: the title shows `total` and the hidden line `inactive`. With Hide sold on and nothing active, the switch stays above "No active listings"; it also stays, with the title count, while the other position loads or fails, so the User can switch back. Removal is delayed. `useFavoriteRemoval` hides the card and owns the deferred DELETE: it goes out only when the 3-second delay ends, another card is removed, the tab loses focus (`useFocusEffect` cleanup) or the screen unmounts, and Undo before that sends nothing; the card comes back in place because it was only filtered out. `useFavoritesView` lowers the counts by the hidden cards and shows the Undo toast above the tab bar (`placement: "aboveTabBar"`); the delete timer is the one clock, and its `onSent` closes the toast so Undo is never offered after the delete. The toast's dismiss area is not accessible while it has an action, so VoiceOver reaches Undo, and the toast is announced with its action on both platforms. The pull-to-refresh spinner shows only for a pull, not for the reload after a confirmed removal. A successful delete drops the Listing from both Hide sold caches and, through `useUnfavoriteListing`, writes ♡ into feed caches and refreshes detail. A failed delete shows the card again with an error toast. Only the latest removal can be undone. Contact buttons stay hidden until the viewer is known. Favorites has no support entry and no recommendations.

The Brand picker (`brands`) picks exactly one brand: a search field sent to the catalog search (any spelling; the picker keeps only brand results, and matches one letter locally because the API ignores it), then Recent, Popular with counts from `/listings/filter-options/brands`, and A to Z. Every row shows `CarBrandLogo`, the uploaded logo tinted with the theme foreground, or the brand's first letter when there is none or it fails to load; a no-affiliation notice closes the list. Tapping a brand pushes the Model picker (`models?brandId=&modelIds=`), which ticks any number of models; none means every model of the brand. Opened from Results, confirmation dismisses back to that existing Results route, preserving its other filters and sort. From Home, "Show N listings" dismisses the pickers and opens Results; "More filters" pushes Search parameters (below); "Change brand" dismisses back to the Brand picker. `pickerActions` owns these per-mode routes, `resultsParams` the picker selection params and `resultsRouteState` the complete persistent applied Results search (still accepting the single `modelId` from "See other Brand Model"), and `useBrandPicker`/`useModelPicker` what each picker shows. Recent (`recentSearches`) is the last 10 confirmed choices, brand-only ones included, de-duplicated by brand and model set with the repeat moved to the top. It lives in AsyncStorage on the device only and is clearable from the Brand picker and Search. It is not a saved search and makes no API call. A failed device write keeps the in-memory list for the session.

Search parameters (`parameters`, `SearchParametersForm`) is a full-screen form for condition, city, brand, model, year and price, replacing the old filter bottom sheet. ⚙ Filters on Results and "More filters" in the Model picker push it, carrying the applied filters and sort as route params (`resultsRouteState`) plus `returnToResults=1` when a Results screen is below it; Search also opens an empty form through All filters, replacing Search over Home. Edits live in the form's own `useListingFilters` draft and nothing is applied until "Show N listings", so Back discards them and leaves Results as it was. Reset clears every field, keeps the sort, and applies nothing until Show N. Show N uses the live count of the draft: it reads Loading while counting, falls back to "Show results" with a Retry when the count fails, and is disabled with "Check filter values" for an inverted year or price range or models without a brand. `showResultsFromParameters` updates the Results below in place with `dismissTo` when `returnToResults` is set, so Results is never stacked twice; with no Results below (the path from Home) it takes the pickers and form off the stack and pushes Results over Home. It also saves a chosen brand to Recent (`useApplyFilterChoice`). The Brand and Model rows open the same pickers in Done mode inside a sheet: no Recent or More filters, and Done writes the brand and models back to the form without applying them.
