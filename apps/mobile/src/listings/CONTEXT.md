# Mobile listings

This area contains create-wizard state, draft persistence, upload staging, edit-save orchestration, discovery state, and listing presentation. The create route and edit route have different orchestration; inspect both before consolidating shared UI. Server lifecycle and contact rules belong to [API Listings](../../../api/src/modules/listings/CONTEXT.md).

## Important constraints

Create flow uses the wizard machine and autosave; edit flow computes and sequences changes against an existing listing. `useSaveListingEdit` runs the sequential best-effort save of [ADR-0025](../../../../docs/adr/0025-edit-save-atomicity.md): it fixes an edit plan when Save starts and keeps a session ledger of the server media IDs attach returned and the media it removed. Reorder, retry and a repeated Save use those server IDs, never a photo's local staging ID, and neither a refetched Listing nor a retry attaches or removes the same photo twice. Retry replays the fixed plan only while the fields and photos are unchanged; edits made after a failure re-plan from the ledger like a fresh Save. Save and Retry return whether they ran, and one runs at a time. Shared contract schemas own validation. Do not make the UI's visual step number a second validation model. Photo UI receives its actual props from the live component interface; old Step2Photos warnings and historical refactor plans are not current requirements.

The Sell wizard has seven steps in the order of `WizardSchemas.WIZARD_STEPS` (founder decision D2 on #354). The step name is the identifier that the mobile machine, `validate-step` and draft saving share; titles come from `wizardSteps.<name>` in the i18n resources. Component file names keep their eight-step numbers, so do not read a position from them.

| # | Step name | Title | Component | Fields |
|---|---|---|---|---|
| 1 | `vehicle` | Car | `Step3VehicleId` with `VinField` | Brand, Model, Year, Generation, then optional VIN (empty or exactly 17 ASCII letters/digits without I, O or Q; no Skip, no auto-fill) |
| 2 | `specs` | Details and condition | `Step4Specs` | Condition, then for Used only Mileage and Damaged / needs repair, then Known issues, then a "More details (optional)" group: Body type, Transmission, Engine, Drive, Color, Power |
| 3 | `photos` | Photos | `Step2Photos` | 3 to 20 photos; guidance toward 8 |
| 4 | `price` | Price | `Step5Price` | Amount, then TMT, USD and AED as inline radio buttons (TMT by default; another currency clears the amount), Exchange, Installment |
| 5 | `location` | Description and place | `Step6Location` with `DescriptionField` | Description (required, up to 2000), then "Where the car can be seen": one City picker grouped by region (`useCityGroups` loads each region's cities; picking a city saves its `regionId` too, so there is no Region row or Region error), and Area (optional, up to 200) |
| 6 | `contact` | Contact | `Step7DescContact` with `ContactPhonePicker` | A verified contact phone (required, also when calls are off), calls and chat switches (at least one on) |
| 7 | `review` | Check and publish | `CheckAndPublish` (create); `EditSectionList` (edit, titled Edit listing) | Create: a card preview, one row per step with Change or Fill in, and the Posting rules line. Edit: the rows only, with Car locked |

A provided VIN is validated by the shared vehicle-step contract; draft storage still accepts partial input for autosave. The Photos step checks camera permission before launching and offers the same localized settings dialog as Profile when the permission can no longer be requested. Call from detail, feed, Favorites and the conversation header uses `openSellerDialer`: it attempts the native dialer directly and shows the contact number if opening fails. No Android package-visibility query is needed for this launch.

The Car pickers chain in one `CatalogPickerSheet` (founder decision D3 on #354): a Brand opens Model, a Model opens Year when none is set or else Generation, and a Year opens Generation when the model has generations and none is chosen. Generation opened by the chain closes itself if the model's generations load empty; closing the sheet ends the chain and keeps every pick. A new Brand clears Model and Generation, a new Model clears Generation, and Year stays. Year is a list from `WIZARD_LIMITS.yearMax` down to 1900 with no search field; the Generation sheet lists all of a model's generations, not filtered by year, and ends with a skip row that clears the generation. The Generation row shows only when the model has generations or one is set.

`Step4Specs` renders in the prototype's order (#609), so the screen-reader order is the visual order and a New car's next control after Condition is Known issues. The optional specs share one "More details (optional)" group with a header-role label; only their order and grouping differ from before, not their fields, rules or stored values. `Step4Specs.order.spec.tsx` pins the New and Used orders.

Each step depends on all earlier ones, and a changed field invalidates its owning step and every later step (`getInvalidatedSteps`; `vin` belongs to `vehicle`, `description` to `location`). The header reads "Step N of 7" and announces the step title with that position when a step opens. Edit uses the same step names but has no step order: it opens on a section list and never opens Car, which is locked with its VIN (see below).

Resume derives completion from the saved fields, never from stored step names. On `INIT` the machine runs every data step's schema against the payload; a create draft opens at the first incomplete step, or at Check and publish when all six pass. A draft saved by the eight-step wizard (names `vin, photos, vehicle, specs, price, location, contact`, VIN first, description on Contact) therefore lands on the right step, and its VIN stays in the payload under Car. The API's draft saving drops step names that no longer exist.

The payload's `currentStep` is the position (1 to 7) of the step the seller was on. `NEXT`, `BACK` and `GO_TO_STEP` write it for a create draft only (an edit has no draft, so its payload never gets one), and the autosave sends it with the payload. `INIT` opens a create draft at that step, but never past the first incomplete step, because later steps depend on it, and writes the step it opened. Back and Continue force-save the payload of the step they move to. Earlier wizards wrote `currentStep` as 1 once and never updated it, and the eight-step wizard could write 8, so a value of 1 or out of range means "not recorded" and the draft opens at its first incomplete step. The cost: a seller who completed Car, went back to it and left on it reopens on Details, not Car. The Drafts card and the Sell row's "steps filled" come from `draftProgress(payload)` and ignore `currentStep`.

✕ in the create wizard header (`sell.tsx` `handleClose`) saves and closes; the draft is already on the server. It builds the same full payload the autosave builds, sends it with `useWizardAutosave().flush` (one attempt, no retry schedule, resolves whether the server holds it), then returns to the Sell tab with a "Saved to Drafts" toast above the tab bar, clear of the Latest draft card. If the last save failed (`saveStatus === "error"`) or the flush fails, `LeaveUnsavedDialog` asks first: Retry flushes again, Leave anyway closes without a toast and keeps the draft as last saved, Keep editing stays. A new Listing the seller never touched is deleted instead of saved, with no toast: tapping New listing still creates the draft at once, so the five-draft check happens before the seller types, and ✕ on that draft (`newDraftIdRef`, set only by `handleCreateNewDraft`) awaits the delete when `isUntouchedPayload(payload)` (every field empty or at its starting value) holds and no photo is picked, so the draft count is right when New listing is tapped again. A draft reopened from the Sell tab or My listings is never deleted by ✕. If the delete fails the empty draft stays and can be deleted from My listings; the same happens when the app is killed with an untouched draft open, since no close ran. The create wizard has no delete or discard action; Delete draft is in My listings only. The edit route has its own leave rule (see the section list below). Android system back is registered while a create wizard is open on a step or a publish error and the Sell tab is the focused screen (`useIsFocused`), so a screen pushed over the tabs keeps its own back: on the first step it behaves as ✕, on later steps it goes back one step, and with the unsaved dialog open it closes the dialog. `useUpdateDraft` and `useDiscardDraft` run with `networkMode: "always"`: offline they fail at once instead of pausing, because ✕ awaits them and a paused mutation never settles; the autosave retries on reconnect itself. ✕ waits at most `CLOSE_WAIT_MS` (10 seconds) for that save or delete: a connected but dead network can hold one request for 30 seconds and a token refresh longer, so a save that has not answered counts as failed and opens the dialog, and an untouched draft whose delete has not answered closes anyway. `useUploadQueue` empties its queue when the staging key changes, so the photos of a closed draft never reach the next one; the emptied queue is not ready (`isReady`) for any draft, so a draft reopened in the same session is read from the device again. Until the queue is ready, Back, Continue, Publish and ✕ save the keyed photos the draft was opened with (`photosToSave`), never the empty queue.

`WizardLayout` shows the save status line under the progress bar as "Saved", "Saving..." or "Not saved. Retry" (nothing before the first save); the error state is a button that retries. It is a polite live region on Android and is announced with `AccessibilityInfo` on iOS. `useWizardAutosave` keeps "Saved" until the next change, and resets its status, error, pending payload and last saved payload whenever the draft id changes, because the hook outlives each wizard session; a save that finishes after the seller left its draft is ignored. A reconnect retries the pending payload through the current draft.

`WizardLayout` is the chrome of every Sell step and of Listing edit. Back is the chevron at the top left of the header, absent on the first step and wherever the machine's `canGoBack` is false; ✕ is at the top right in create and at the top left of an edit's section list. The bottom holds one full-width action (Continue, Done, Publish or Save changes) with its hint, blockers or publish error above it. It is laid out below the scrolling step on the page background, not floating over it, so no step content shows under the button.

Photos continues on three picked photos, in any upload state: `StepPhotosSchema` wants three entries in `photos`, key or not, so uploads keep running while the seller fills in the later steps. `sell.tsx` therefore keeps two views of the queue. The machine payload's `photos` lists every picked photo (`buildPickedPhotos`) and is synced only when the set or order of photos changes, never when a key arrives, so a finished upload does not reset the steps after Photos. What is autosaved, force-saved and published is only the photos with a key (`buildPayloadPhotos`), because the API treats a draft photo as attached and publication requires three keyed photos. The publish gate holds Publish while any photo is uploading, queued, waiting for the network, failed or lost, and the wizard says why above Publish ("Photos still uploading: N", "Photos failed: N. Retry or remove them."). `countUploads` (`uploadStaging/uploadCounts`) is the one count behind the header chip and that text. The chip sits in the wizard header on every step and opens Photos. On Photos, a tap on a tile opens `PhotoActionSheet` (Retry for a retryable failure, Set as cover and Move earlier unless first, Move later unless last, Remove; Set as cover is not offered for a failed or lost photo, though Move earlier or a drag can still put one first), a long press still drags to reorder, and every failed or lost photo is also listed under the grid with its reason and Retry or Remove. Each tile announces itself as "Photo N of M" with Cover and its upload state. Edit shares `Step2Photos` but keeps its own payload sync, which saves keyed photos only, so there Done still waits for three uploaded photos and the "You can continue" line is left out (`continuesWhileUploading={false}`); its chip and Save changes reason use the same `countUploads`. A photo that was compressed but not uploaded when the app closed is not in the saved draft: `reconstructQueueFromDraft` brings its staged file back as `compressed`, `useUploadQueue` queues it once the queue is initialized (`isReady`), and that first sync of a resumed draft keeps the steps that are still valid (`UPDATE_FIELDS` with `keepValidSteps`) instead of resetting the ones after Photos. Until `isReady` is true for the open draft the queue is empty or still holds the last draft's photos, so `sell.tsx` neither syncs it into the payload nor autosaves from it. The hook starts one initialization per staging key, and a photo already waiting or uploading is not queued a second time by a resume from the app or the network.

Check and publish in the create wizard is `CheckAndPublish` (#588). It shows the Listing as a card (cover photo, the price in the draft's own currency, spec line, "Brand Model, year", city) over "This is how buyers will see your listing", then one row per step with a one-line summary and Change, or Fill in when the step is not in `validatedSteps` (and on Photos while a photo has failed or is lost), then a line that opens the Posting rules page for the app language. "Damaged / needs repair: Yes/No" is stated for a Used car only. Until the upload queue is ready (`photosReady`) Check shows no photos and does not say "No photos". A row dispatches `CHANGE_FROM_REVIEW`, which sets the machine's `changingFromReview`: the step shows Done in place of Continue (`editDetourActive`), and Done (`RETURN_TO_REVIEW`, only when the step is valid) or Back returns to Check. Both read completion from the fields again (`completedSteps`), because a changed field resets the steps after its own; so a change that leaves the later steps valid keeps Publish available, and a step left invalid with Back is named on Check. The header's upload chip opens Photos the same way when tapped on Check. A step reached with the header's Back is not such a change and keeps Continue.

Editing a published Listing opens on a section list (#589), `EditSectionList` in the same file as `CheckAndPublish`: its rows and summaries without the preview, the Posting rules line or Publish, under the heading "Edit listing" and the note that buyers see changes only after a save. `WizardLayout` draws that list with `sectionList`: ✕ on the left and the title with the car's title under it (`useCarTitle`, "Brand Model, year"). In edit mode no header has a step position or a progress bar: a step opened from the list has Back, "Edit listing" over the car's title in the top row, and the step title alone, announced without a position. The Car row is not a button: it has no Change, shows why ("Brand, model, generation, year and VIN cannot be changed after publishing.") and is announced as disabled, and `CHANGE_FROM_REVIEW` refuses `vehicle` in edit mode, so the edit route renders no Car step. Every other row dispatches the same `CHANGE_FROM_REVIEW` as Check: the step shows Done, Done (`RETURN_TO_REVIEW`) returns only when the step is valid, and Back returns either way, after which the list names an invalid step with Fill in. A legacy Used Listing with no Damaged answer opens on Details as such a change. Changes stay in the session until Save changes (ADR-0024, ADR-0025).

`hasEditChanges` (`edit/editChanges.ts`) decides whether the edit differs from the published Listing: any field Save changes would send (`EDITABLE_FIELDS`), with an empty value equal to a missing one, or the photos and their order once the upload queue is ready. After a failed save the session counts as changed until a save succeeds, because part of it may be on the server. Save changes is enabled only while it is true, the steps are valid, no photo is uploading or failed, and no new contact number still needs a code (that row then reads Fill in); undoing every change disables it again. ✕ and Android system back on the list close at once without changes and otherwise open `LeaveEditDialog` ("Leave edit mode?", Leave, Keep editing); system back on a step returns to the list, a second back closes the dialog, and the handler is registered only while the edit is the focused screen, so the contact phone screens keep their own back. The iOS swipe back cannot ask first, so the route's `Stack.Screen` turns it off (`gestureEnabled`) while the edit has changes. Leaving deletes the edit's staged photos. A successful save toasts "Changes saved" and replaces the edit with the Listing. A failed save stays on the list with "Couldn't save all changes. Try again.", the state of each operation and Retry, announced to a screen reader, and keeps every change; the header's "Not saved. Retry" retries too. The route accepts any Listing the server returns; which statuses offer Edit is decided by `ownerListingActions` (active and removed, not sold or blocked).

Above Publish, `publishBlockerLines` lists what blocks it, in the order a screen reader reads: "Fill in: Car, Price" naming each incomplete step, then "At least 3 photos are required" while the queue holds fewer than `MIN_LISTING_PHOTOS` photos, then photos still uploading, then photos that failed; Publish is disabled while any line shows, and photo counts are left out until the queue is ready. Until then Publish is disabled too, with the neutral "Loading..." line in place of a blocker. Tapping Publish saves the draft, shows "Publishing..." and takes no second tap (`publishingRef` in the route, and the disabled button). The save is one attempt (`flush`), so no retry can change the draft after it is published. When it fails no publish is sent: `PUBLISH_ABORTED` returns the machine to Check with no publish error, and the save status line ("Not saved. Retry") and the save error banner say what went wrong. On success the route toasts "Listing published", replaces the wizard with the Listing, and resets the machine so the Sell tab is back at its entry; `usePublishDraft` invalidates the drafts and My listings queries. There is no success screen and no Share. On failure the machine goes to `publishError` and stays on Check: `publishFailureOf` sorts the error into photos (`PHOTO_MINIMUM_REQUIRED`, or an `INVALID_DRAFT_PAYLOAD` whose `formErrors` name `AT_LEAST_THREE_PHOTOS_REQUIRED` or the older `AT_LEAST_ONE_PHOTO_REQUIRED`; worded "At least 3 photos are required"), offline (`NETWORK_ERROR`), `EXCHANGE_RATE_MISSING` (worded with the draft's currency) or server, and `WizardLayout` shows the message above Publish as an assertive alert, announced with `announceForAccessibility` on both platforms. The server's own message is never shown and there is no failure toast. Publish, Back and Change all work from `publishError`. `usePublishDraft` runs with `networkMode: "always"`, so offline it fails at once instead of pausing with "Publishing..." on screen. The contact phone rejections (`CONTACT_PHONE_NOT_CONFIRMED`, `CONTACT_PHONE_REQUIRED`) are routed to the Contact step before `publishFailureOf`; see below.

The contact phone is picked, not typed ([ADR-0056](../../../../docs/adr/0056-listing-contact-phones-are-verified.md), [ADR-0081](../../../../docs/adr/0081-contact-phone-confirmation-api-for-listings.md)). `ContactPhonePicker` lists the seller's sign-in phone first (from `useAuth`, preselected on a fresh draft, no code), then the numbers `useMyContactPhones` returns with the days left from `reusableUntil` (`contactPhoneDaysLeft`), then "Another number". `GET /me/contact-phones` leaves out the sign-in phone, and its query key carries the User ID so the next User never sees the list. `resolveContactPhoneSelection` names what the chosen number is worth: `account`, `confirmed`, `current` (the Listing's own number while editing), `pending`, `stale` or `none`. A `stale` number, for example a draft's saved number past its 7 days, is shown once as "Confirmation expired. Tap to confirm again." and cannot be selected; a listed number with no days left is not a quick pick. `pending` is a saved number the app cannot judge because the confirmed list is still loading or its request failed: it stays a plain chosen row and does not hold Continue, and the server still refuses it at publish if it is not confirmed. Once a publish has refused it, the row is the expired one and Done is held. Selectable rows are radios and the expired row is a button; each is labelled with its number and sub line. Continue on the Contact step stays tappable so a `stale` or `none` selection can show its error instead of advancing; the route owns that check, because `validate-step` is only a format check. An email-only User has no preselected number and reads why a phone is still asked.

"Another number" and an expired row push `app/listings/contact-phone.tsx` (a `+993` number, Send code) and then `contact-phone-code.tsx` (six cells, resend countdown, the line saying what the code allows). The caller passes its own path as `returnPathname`; `contactPhoneReturnHref` accepts only the Sell wizard, My listings, a Listing's edit screen and Listing detail, and the screens return with `router.dismissTo` and a `confirmedContactPhone` param that the caller puts in its payload and then clears. A number the server already trusts (`status: "confirmed"`) skips the code screen, and `useRequestContactPhoneCode` then refetches the confirmed list, because the number may have been confirmed on another device. `contactPhoneError.ts` maps the request and verify errors: the daily limit (`destination_limit`) shows fixed copy with one Help link and no time, a `backoff` refusal shows the wait, `INVALID_OTP` shows the attempts left, and a locked or expired code stops entry and offers "Send a new code". A backoff refusal on the code screen, also from the locked or expired state, shows the wait and holds the button for its countdown.

The server repeats the check, so three refusals come back to these screens. A publish refused with `CONTACT_PHONE_NOT_CONFIRMED` or `CONTACT_PHONE_REQUIRED` is not a `PublishFailure`: `sell.tsx` catches it before `publishFailureOf`, dispatches `PUBLISH_ABORTED` and then `CHANGE_FROM_REVIEW` to Contact, so the draft is kept, Check shows no publish error, the Contact step reads "Confirm the contact phone again to publish." and Done returns to Check. The edit screen shows the same picker with the Listing's current number selectable without a code; the API checks an edit only when it changes the number, and a save it refuses for that reason opens the Contact step, saves nothing and leaves the other changes in the session. A relist refused with `CONTACT_PHONE_NOT_CONFIRMED` opens `RelistContactPhoneSheet` (My listings and the owner actions on detail), which confirms the Listing's own number only. Its Send code asks for the code and opens the code screen, which relists once the code is accepted and offers no "Change number"; a number the server already trusts relists from the sheet at once. A refused request (daily limit with the Help link, backoff wait, offline) or a failed relist is worded in the sheet, which stays open. `CONTACT_PHONE_REQUIRED` on relist tells the seller to add a phone through Edit; on detail that hint clears when the next owner action starts.

Publishing depends on required fields, contact verification, and successful media attachment. A file appearing in a preview does not prove it was uploaded or attached. Preserve retry state and draft reconstruction, and inspect the queue, publish-gate code, and tests when changing navigation or autosave timing.

The signed-in Sell tab entry is `SellEntry` (`src/listings/sell`); the signed-out entry stays in the route. It reads `useMyDrafts` (newest first) and shows a skeleton, the shared `ErrorState` with Retry, a first-listing entry, or the latest draft row with Continue, New listing, "All drafts" (two or more) and My listings. Steps filled comes from the shared `draftProgress(payload)`, the same count the Drafts card shows, so the two cannot disagree. Its total is every wizard step, Check and publish included, so it matches the header's "Step N of 7"; only the six data steps can be filled. New listing at `MAX_DRAFTS_PER_USER` drafts, or an API `DRAFT_LIMIT_REACHED` refusal, opens the limit sheet instead of creating a draft. "All drafts" and the sheet open My listings with `tab=drafts`; `manage.tsx` opens on any known tab named by that parameter.

The condition disclosure is one required Yes/No question, **Damaged / needs repair**, plus optional **Known issues** ([ADR-0052](../../../../docs/adr/0052-seller-condition-disclosure-is-damaged-plus-known-issues.md)). For a Used car, the Details and condition step leaves it unanswered until the seller picks one, and the shared `StepSpecsSchema` blocks the step (`wizardErrors.damagedRequired`) until then. For a New car the question is hidden and the draft stores `damaged: false`; switching New to Used clears that answer and asks again, and a damaged New draft shows `wizardErrors.damagedNotForNew` under Condition ([ADR-0080](../../../../docs/adr/0080-a-new-car-skips-the-damaged-question.md)). A legacy Used Listing without an answer enters edit at the specs question before the seller can save; a New one enters at review. Sell and Edit keep Mileage, Engine power and disclosure errors quiet until that field is touched or the specs step is attempted; changing New to Used starts with untouched, unanswered Used questions. Specs Continue/Done accepts an invalid-field attempt, reveals the errors, and stays on the step; other invalid-step controls stay disabled. Pending operations still block the footer. Create-wizard load derives `damaged: false` only for a missing New answer, preserving explicit `true` for rejection. A submitted disclosure replaces Known issues, so clearing the input removes the saved text. Listing detail shows it under "Condition, as stated by the seller" and renders nothing when a Listing has no answer.

Listing detail follows the approved Auto.ru content order with AutoTM tokens: photos and numeric counter, title, price, date/city, six key specifications followed by rows, expandable seller description, seller-stated condition, Seller card, Report, and public-number/date footer. Between the description and the seller's condition statement sits Ask the seller. The route owns the sticky Call/Message or owner Edit/Mark sold bar, measured gallery scroll threshold, header actions and Report sign-in/replay. The owner bar and menu take their actions and names from `ownerListingActions`, shared with My listings: Edit and Mark as sold in the bar, then Remove from sale and Delete in the menu (Relist and Delete for a removed Listing, Delete alone for a sold one, which cannot go back on sale). Listing detail hides both Share and Copy link until a public web Listing page and App Links exist (#495, decided in #322); the buyer overflow holds only Report on active Listings, and its trigger is hidden whenever Report is unavailable (sold/archived, or reporting disabled) so no empty menu opens. Saves appear only in the owner status card; it shows no view count, because nothing counts Listing views yet (32 Listings still describes one). On a loaded, open Listing that takes no calls or has no contact phone, `ContactCtaBar` leaves Call out and Message takes the full width, on the page and in the photo viewer; loading, sold and archived keep a disabled Call. Sold/archived buyers retain the banner, muted price and similar brand/model link, with contact, Favorite and Report hidden. A 404 offers Home and Back.

My listings (`app/listings/manage.tsx`) has three tabs, Active, Drafts and Archive, and opens on the one its `tab` route parameter names. `GET /me/listings` has no status filter, so the screen filters on the client: Active holds active and blocked (banned) Listings, Archive sold and removed ones, labelled. Each tab shows its count from `useMyListingCounts` (Active = active + banned, Archive = sold + archived), and none while the counts load, after a failure or at zero. A blocked row shows a neutral note and has no ⋯ and no tap. Every other row's ⋯ opens `OwnerActionSheet` with the actions `ownerListingActions` allows for its status (drafts get Continue and Delete draft); every action but Edit and Continue asks first, and a toast confirms or says it failed. The invalidated lists and counts refetch, so a changed row moves to its new tab. Each tab has skeleton rows, the shared `ErrorState` with Retry, and its own empty state.

Tapping a gallery photo opens `PhotoViewer`: a black full-screen Modal with an `n / N` counter, ✕, swipe paging, a thumbnail strip, and ♡ plus Call + Message. `PhotoGallery` takes the ♡ and the contact bar as render props, so the gallery itself knows nothing about auth; `ListingDetailView` supplies `ViewerFavorite` and a second `ContactCtaBar` (`variant="viewer"`, `replayAuth={false}` so a Message replayed after sign-in opens one Conversation, not two), and supplies neither to the owner or on a sold or archived Listing. A React Native Modal sits above the navigation stack and would hide the sign-in screen, so every viewer action that leaves the screen closes the viewer first (the slots receive `close`). Closing, by ✕ or the system back gesture, hands the photo the viewer was left on to the gallery, which scrolls there. `ZoomableImage` does pinch, drag-while-zoomed and double-tap with Gesture Handler and Reanimated shared values (`zoomMath` holds the clamps), reports only zoomed or fitted to React, and the viewer locks paging while a photo is zoomed. The Modal wraps its content in `GestureHandlerRootView`, as Gesture Handler requires on Android. These gestures run on the UI thread, so the Vitest adapter mocks them and only a device proves them; swipe-down to close, shown as a hint in the prototype, is not implemented.

Listing detail opens instantly from the tapped card. `useListingPreview` reads the card's `ListingSummary` by Listing ID from the feed and Results lists (`queryKeys.listings.lists()`, whatever the filters or viewer), Favorites and My listings caches, and `ListingPreview` shows its photo (the `list` variant the card already decoded), title, price, spec line (`km · gearbox · fuel`), date and city, with the rest behind skeletons and Call and Message disabled until the detail query returns. It is a separate value, not `initialData` or `placeholderData` on the detail query: a summary lacks contact, description and seller, and must never pass for a loaded Listing. The owner and closed Listings get no bar while loading, from the summary's seller and status. A deep link, or a card the cache has evicted, finds nothing and shows the plain `DetailSkeleton`.

Ask the seller (`AskSellerChips`) offers the four QuickReplies intents as chips. A tap opens the Conversation through `useOpenListingConversation` (shared with the Message button) and passes the question as a `draft` route param; the Conversation seeds `MessageComposer` with it through `initialText`, and the buyer still presses Send. Signed out, the chosen intent is parked as `{ kind: "ask", intent }` behind `requireSignIn` and finished on return, resolved to text in the current locale. The chips are hidden for the owner, for sold and archived Listings, and when the seller turned chat off, as Message is disabled then. The four intents are fixed in `QuickReplies`; this feature adds none.

The Seller card shows the seller's avatar at 44 points (`PublicUserAvatar`: the profile photo, or the car mark for `seller.avatarIndex`), then the name, "Private seller", the join month, and city/place. The name is the one the seller set or their Generated Name in the app language ("Driver 2057"), so "Private seller" is always the second line and never the title; only a deleted seller (`seller.deleted`) has it as the title, with the neutral person icon. The card is not drawn on the viewer's own Listing. It has no Phone verified badge; Call carries the SMS-verification caption under ADR-0056. VIN remains a specification row when present; the decoding section renders only for `vinHistory.decoded === true`, with no empty state under ADR-0053. ADR-0057 keeps the inspection component, hook and tests unused: detail no longer renders its entry or reads the inspection config, and publishing no longer requests its sheet. The API endpoint and decoder code remain unchanged.

Picker URIs are copied into persistent temporary storage before parallel compression because iOS may reclaim picker cache files under memory pressure. The compressor copies its result into staging, verifies the destination, and cleans temporary files best-effort. Preserve copy rather than cross-directory move; earlier iOS failures motivated that choice. Overlapping compression/upload operations use reference counters, since a boolean can clear while another operation is still active.

The compressor currently uses the contextual ImageManipulator chain. Consult current Expo docs before an SDK change; historical API notes cannot establish present library support. Staging cleanup is local-device cleanup, distinct from the worker's broad orphan-cleanup queue.

Search/filter UI separates editing state from applied query state. Check the stores, serializers, query keys, and API ranking adapter together when changing filters or result counts. Approved discovery requirements are in the Search specification, not old planned-refactor notes.

Home (`app/(tabs)/(search)/index.tsx`) is the root of the Search tab's own stack, anchored at `index` so a deep link still has Home underneath. `AutoTmTabBar` always emits `tabPress` and navigates only to an unfocused tab, so re-tapping Search pops to Home while other tabs keep their history. Home has no filters: a Brand/model card with the live count and a two-column New listings grid of `ListingGridCard`. Search renders Recent and Popular before typing, then combined brand/model catalog matches. The debounced catalog API owns spelling and year parsing; Search passes its year bounds into Results as `yearMin`/`yearMax` route params. A bare year opens the full feed with that year range, while an unmatched name with a year stays no match. Settling and placeholder results cannot be selected. Search keeps its input editable through loading, errors and offline-paused queries, retries after connection recovery, and opens the keyboard on entry. Back dismisses the keyboard and goes back to the Home underneath through `useSafeBack` (Home is only the fallback when there is no history), so Search never stacks a second Home; a pick replaces Search with Results, so Back from Results returns to Home. All filters replaces Search with Search parameters over Home. Results keeps applied filters and one of the six approved sort orders in route search params, so deep links and Back restore the same search. Its header reads the live matching count and TMT range. Condition and removable city/price/year chips commit in place, with the chips floating at the bottom once the header scrolls away. A single brand/model card shows the chosen brand's `CarBrandLogo` (its letter when there is no logo; the generic car only when no brand is chosen), opens the current ticked models and can clear the selection. "Reset filters" on a no-match Results clears the filters but keeps the current sort. The list stays mounted behind Listing and sign-in navigation, preserving its native scroll position. Results uses `ListingLargeCard`, a card the full width of the screen with rounded corners: a photo strip (`ListingPhotoStrip`) of the feed item's `galleryKeys` (up to eight; an older API's two `photoKeys` otherwise), each photo 61% of the card wide (4:3) with rounded corners and snapping one per swipe, ending with a "+N photos" tile that opens the Listing when the Listing has more photos than keys; one photo fills the frame, and none gives one "No photos" frame of the same height. The strip sits 8 dp inside the card's top and left edges (`STRIP_INSET`); that gap is padding on the scrolling content, so a swipe carries the photos through it and out to the card's right edge. The 📷 count and a seller-stated New sit on the photos. Below: the TMT price in plain bold text, available mileage/gearbox/fuel names, one-line brand/model/year, then Call, Message and ♡, then the seller's name and "Private seller · city · date" (`feedCardFields` reads the feed-only fields). Call and Message show only when the feed item allows them, the viewer is known and the Listing is not the viewer's own. Call needs no sign-in: it reads the contact phone on tap through the Listing detail query (`listingDetailQueryOptions`, same key as detail; `useListingCall`) and dials only what detail would offer. Message opens the Conversation, or, signed out, parks `{ kind: "message" }` behind `requireSignIn` with Results as `returnTo`; `FeedMessageReplay` finishes it on the screen. A deleted seller shows Private seller alone, as detail does. The skeleton has the card's shape. A signed-out ♡ on a card stores a pending Favorite; `useFeedFavoriteReplay` finishes it at screen level when the owning Home or Results screen regains focus, because the tapped card may no longer be mounted. Feed cards and Listing detail share `useListingFavorite` (#813): a tap shows at once, with `Pop` and never a spinner or a disabled ♡, and is written into the cached feed pages and detail so every card of the Listing agrees; taps queue, the requests go out one at a time until the server holds the last tapped state, and a failure puts back the last confirmed state. While nothing is in flight the ♡ is the cached `isFavorited`, so a refetch always corrects it. `setFeedFavorited` writes a ♡ state only into signed-in cached feed pages, because a silent sign-out keeps the query cache and Home would otherwise show the previous User's ♥.

Favorites (`app/(tabs)/favorites.tsx`) uses its own `FavoriteListingCard` with `isOwn` and `onRemoveFavorite`, built from the Results card's parts (#807): full width with a 28 dp radius, `ListingPhotoStrip` of the item's `galleryKeys` (two `photoKeys` from an older API; `feedCardPhotoKeys`), the same text order, and Call, a square Message (`SquareAction`) and a square filled ♥ in one row; with no contact buttons the ♥ ends the city and date line. Call opens the dialer with the Listing contact phone when the seller allows calls and gave one, Message opens the Conversation through `useOpenListingConversation` when chat is on (a failure shows `ErrorState` under the buttons), neither shows on the User's own Listing, and the filled ♥ removes the Favorite. Sold and archived Listings are dimmed and labelled Sold or Removed from sale, with a muted price and no contact buttons; the card still opens Listing detail. `useFavoritesView` owns what the tab shows. Hide sold (`HideSoldToggle`, one row with the `switch` role) starts on and lives in an in-memory zustand store, so it survives tab changes while the app runs but is never stored on the device. Its position picks the `useMyFavorites({ activeOnly })` list, keyed separately per position (`queryKeys.favorites.list(activeOnly)`, prefix `lists()`), and every page carries `counts` over all visible Favorites: the title shows `total` and the hidden line `inactive`. With Hide sold on and nothing active, the switch stays above "No active listings"; it also stays, with the title count, while the other position loads or fails, so the User can switch back. Removal is delayed. `useFavoriteRemoval` hides the card and owns the deferred DELETE: it goes out only when the 3-second delay ends, another card is removed, the tab loses focus (`useFocusEffect` cleanup) or the screen unmounts, and Undo before that sends nothing; the card comes back in place because it was only filtered out. `useFavoritesView` lowers the counts by the hidden cards and shows the Undo toast above the tab bar (`placement: "aboveTabBar"`); the delete timer is the one clock, and its `onSent` closes the toast so Undo is never offered after the delete. The toast's dismiss area is not accessible while it has an action, so VoiceOver reaches Undo, and the toast is announced with its action on both platforms. The pull-to-refresh spinner shows only for a pull, not for the reload after a confirmed removal. A successful delete drops the Listing from both Hide sold caches and, through `useUnfavoriteListing`, writes ♡ into feed caches and refreshes detail. A failed delete shows the card again with an error toast. Only the latest removal can be undone. Contact buttons stay hidden until the viewer is known. Favorites has no support entry and no recommendations.

The Brand picker (`brands`) picks exactly one brand: a search field sent to the catalog search (any spelling; the picker keeps only brand results, and matches one letter locally because the API ignores it), then Recent, Popular with counts from `/listings/filter-options/brands`, and A to Z. Every row shows `CarBrandLogo`, the uploaded logo tinted with the theme foreground, or the brand's first letter when there is none or it fails to load. The no-affiliation notice for brand names and logos (#350) is on About the app, not in the picker. Tapping a brand pushes the Model picker (`models?brandId=&modelIds=`), which ticks any number of models; none means every model of the brand. Opened from Results, confirmation dismisses back to that existing Results route, preserving its other filters and sort. From Home, "Show N listings" dismisses the pickers and opens Results; "More filters" pushes Search parameters (below); "Change brand" dismisses back to the Brand picker. `pickerActions` owns these per-mode routes, `resultsParams` the picker selection params and `resultsRouteState` the complete persistent applied Results search (still accepting the single `modelId` from "See other Brand Model"), and `useBrandPicker`/`useModelPicker` what each picker shows. Recent (`recentSearches`) is the last 10 confirmed choices, brand-only ones included, de-duplicated by brand and model set with the repeat moved to the top. It lives in AsyncStorage on the device only and is clearable from the Brand picker and Search. It is not a saved search and makes no API call. A failed device write keeps the in-memory list for the session.

Search parameters (`parameters`, `SearchParametersForm`) is a full-screen form for condition, city, brand, model, year and price, replacing the old filter bottom sheet. ⚙ Filters on Results and "More filters" in the Model picker push it, carrying the applied filters and sort as route params (`resultsRouteState`) plus `returnToResults=1` when a Results screen is below it; Search also opens an empty form through All filters, replacing Search over Home. Edits live in the form's own `useListingFilters` draft and nothing is applied until "Show N listings", so Back discards them and leaves Results as it was. Reset clears every field, keeps the sort, and applies nothing until Show N. Show N uses the live count of the draft: it reads Loading while counting, falls back to "Show results" with a Retry when the count fails, and is disabled with "Check filter values" for an inverted year or price range or models without a brand. `showResultsFromParameters` updates the Results below in place with `dismissTo` when `returnToResults` is set, so Results is never stacked twice; with no Results below (the path from Home) it takes the pickers and form off the stack and pushes Results over Home. It also saves a chosen brand to Recent (`useApplyFilterChoice`). The Brand and Model rows open the same pickers in Done mode inside a sheet: no Recent or More filters, and Done writes the brand and models back to the form without applying them.

The native Listing upload queue requests optional `conditional-v1` image presign and forwards the returned required headers unchanged, including the quoted `if-match` ETag. A response without headers uses the installed legacy PUT shape, allowing older API builds to ignore the opt-in. Do not retry an issued conditional URL without its header or recreate missing objects; queue retries obtain a new presign. Chat has its own upload path. Real deployed native upload/provider proof remains part of release verification.

The shared `compressPhoto` helper accepts a target long side and source dimensions for Profile Photos. Omitting that target preserves the Listing default of 2400 points wide; Profile uses 512 on the long side and does not use the Listing queue.
