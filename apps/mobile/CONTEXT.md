# Mobile application

Mobile is the primary marketplace client. The route tree, API hooks, feature modules, and colocated tests establish current behavior. Use the [Listings overview](src/listings/CONTEXT.md) for create/edit, upload staging, and discovery state.

## Boundaries that matter

- External legal and listing links use `src/config/publicWebUrl.ts` and `EXPO_PUBLIC_WEB_URL`. EAS profiles select the staging or reviewer-production public web origin; the native account deletion action still opens its in-app route.
- In-app account deletion (`app/account/delete.tsx`) uses the session alone, never a code, and needs the "I understand" tick ([ADR-0032](../../docs/adr/0032-account-deletion-grace-period.md)). The API does not return the deletion date, so the app shows today plus 30 days. Success clears the session and query cache, then shows `app/account/deletion-scheduled.tsx` over signed-out Cabinet, so no Back returns to a signed-in screen. Failure keeps the User signed in on the screen.
- Support contacts live only in `src/config/supportContacts.ts`. Help, `/help`, shows them. Help and the signed-in Messages Support row open the same personal case through `src/services`; its server admission remains synthetic-only and separate from paid Vehicle History.
- Counted copy uses i18next plural keys (`_one`/`_few`/`_many`/`_other`). Hermes has no `Intl.PluralRules`, so `initI18n` installs the partial ru/en/tk rules in `src/i18n/pluralRules.ts`; a library needing full `Intl.PluralRules` needs a real polyfill through the [mobile package gate](../../docs/agents/mobile-expo.md).
- All API calls go through `src/api/client.ts`; it owns single-flight refresh, both after a 401 and before sending when the stored token has passed its lifetime ([ADR-0063](../../docs/adr/0063-mobile-refreshes-an-expired-access-token-before-sending.md)). It clears the session only on a 401 from `/auth/refresh` or a 2xx JSON body that breaks the contract; a 5xx, network failure or unreadable answer keeps it ([ADR-0077](../../docs/adr/0077-mobile-keeps-the-session-when-a-token-refresh-fails-without-a-rejection.md)). Before storing or clearing a refresh result, the client checks that the stored User id and refresh token still match the session that started it. Individual request cancellation cannot block shared token rotation or other callers. Hooks use shared contracts and query-key factories. Keep session isolation and cache cleanup when identity changes. Follow the [data-fetching guide](../../docs/agents/mobile-data-fetching.md) before changing this boundary.
- Functional text links use `text-link`, mapped to the same `--message-read` semantic blue as read indicators: blue600 in light mode and blue400 in dark mode. This includes link buttons such as More, account link values, sign-in legal links and wizard editing/contact actions. Brand actions retain Carberk red; info-status badges/toasts retain their separate palette role.
- Mobile components use React Native Reusables under `components/ui`. Shared browser components are not native components. Follow the [styling guide](../../docs/agents/nativewind-v4.md); actual tokens, utilities, and fonts are in the app configuration and theme sources.
- Sign-in Methods and listing contact phones have different meanings. Preserve auth-on-action for anonymous browsing, and use the glossary when changing identity/contact flows.
- Cabinet's diagnostic history opens current orders and released reports through `src/diagnostics`. Private readers isolate queries by User and discard cached data on exit or failed revalidation. Public Results/detail report actions use a separate anonymous availability projection without changing Listing rank or view counts. Readers show complete findings, body-map text equivalents, corrections and explicit per-locale PDF readiness. Native document handling uses the protected temporary-file action; storage locators never reach the client. Actual center activation and device PDF open/share acceptance remain separate gates.
- `components/auth/CodeEntryForm.tsx` is the one Sign-in Code screen for sign-in and for adding or changing a Sign-in Method. A request refused with `RATE_LIMITED` and `details.reason = "destination_limit"` (`src/auth/requestOtpError.ts`) is the daily limit: the entry screens say so, and the code screen hides Resend, stops taking digits and offers Contact support, its only link to Help. Other refusals keep the wait-a-moment copy.
- Phone/email sign-in URLs share `components/auth/SignInEntryScreen.tsx`. Method values stay local to the mounted entry, switching creates no route, and one native input changes keyboard type in place. `src/auth/signInEntryReturn.ts` connects Code return to that mounted entry only; it stores no values or account purposes. Leaving the root entry abandons unfinished intent once; completed replay survives. Account add/change stays on its separate fixed-purpose routes.
- Auth-on-action stores a serializable pending action in `src/auth/intentStore.ts`. Screens replay it with `useReplayAuthAction`, or, for a screen-level consumer such as Home's feed, `useReplayAuthActionOfKind` while focused.
- Cabinet, `/(tabs)/services`, is the menu; there is no Settings screen. Its rows use `components/account/MenuRow.tsx` and never wait for the network, except the profile row, which waits for `/me`. The My listings row shows `total` from `GET /me/listings/counts` (`useMyListingCounts`, keyed per User) as its value, with no number while it loads, fails or is zero; mutations that change inventory or Listing state invalidate it, and the row refreshes when Cabinet comes back into view. Log out and Delete account sit at the bottom of Profile, and logging out lands on Cabinet, signed out.
- Every signed-in User is shown with a Display Name and an avatar, both read from `/me` (`useMe`), never from the stored session, which carries neither `nameNumber` nor `avatarIndex`. `src/identity/useDisplayName.ts` gives the name the User set or the Generated Name in the app language. `components/identity/UserAvatar.tsx` draws the avatar at any size: the Profile Photo when `avatarKey` is set, using `avatarUrl` when supplied or the Listing thumbnail variant from the key, otherwise the Assigned Avatar from `src/identity/carAvatars.ts`. That file holds the twelve marks in the order the server counts them; the order may only grow at the end, and an index outside the set wraps around it. The twelve tints are the only colours there that are not app tokens. The avatar takes an accessibility label only where no name sits beside it. Cabinet's profile row and Profile's header use both. The signed-out row and a failed `/me` keep the person icon. `PublicUserAvatar` uses the same Listing photo variants for public identities (see `src/conversations/CONTEXT.md`).
- Profile's camera-badged avatar opens `ProfilePhotoSheet`: the system library picker with no library permission prompt, the system camera with a camera permission dialog/settings link, and Remove when a photo is set. Both library and camera retain native square cropping on iOS; Android shows no native crop screen, bypassing SDK 55's unsafe crop result. `useProfilePhotoUpload` uses decoded, orientation-corrected dimensions to resize the short side to 512 pixels and centre-crop a 512 × 512 square before JPEG compression. It accepts readable source formats without a MIME allowlist, handles decode failure as unsupported and checks the 5 MB output limit locally. It uses a standalone FileSystem task with measured byte progress or an indeterminate spinner before byte progress is available, retaining the last measured percentage after invalid/unknown-total events and using photo-specific upload text in EN/RU/TK, not the Listing draft queue, with `kind: "image"`, `writeProtocol: "conditional-v1"` and the returned conditional headers. The set/remove hooks validate the complete `/me` response and write the shared cache, so Cabinet updates too. Jobs and recovery selections outlive the Profile route but are bound to the initiating session: sign-out hides its preview and late requests/results cannot reach a later User. API auth and refresh stay in `apiClient`, with photo ownership checks in each request before sending or retrying, outside the shared refresh. Retry taps share one job per selection. Storage PUT has a 60-second deadline and ignores late progress after it ends; rejected tasks, cancellation and session end release the native task's progress subscription. `UPLOAD_PREPARING` polls the same key at most 30 times, with Cancel and session end stopping the waiting timer; exhaustion offers Retry. Other adoption refusals retry with a fresh presign. Upload/removal failures and offline state use the box below the header; invalid local files offer another selection. Success uses Profile's notice line. iOS announces start, preparing and results instead of each percent. Native camera/photo permission purposes cover Listings and Profile Photos in EN/RU/TK. Native picker, progress, storage-provider and visual evidence still require the separate development-build emulator/device pass. The [issue 758 verification record](../../docs/evidence/issue-758/verification.md) distinguishes proven code defects from the original sticky-upload failure, which is not proven fixed and requires a separate reproduction/logcat follow-up.
- Profile changes a held Sign-in Method only after a confirm sheet, and adds a missing one directly; nothing removes one. A value another User holds is refused after the code with its own screen, `/account/sign-in-method-taken`, opened on top of Profile; it never offers to switch or merge accounts. The entry screens refuse the value the User already holds before sending a code. The code screen hands Profile its "Added" or "Changed" line, and the name editor its "Name saved" line, through `src/identity/profileNotice.ts`, shown in the page rather than as a toast so it covers no control. Photo upload and removal use this line too.
- The name in Profile's header, with its pencil, opens the name editor, `/account/display-name`. The field opens holding the name others see now, set or generated, and takes up to 40 characters so a name past 30 shows its error instead of being cut. `src/identity/displayNameField.ts` applies the rule from `@auto-tm/contracts`, the one the API applies, and tells an empty field from one of only spaces; errors show after the first edit. Save needs a valid name that differs from the current one. `useUpdateDisplayName` sends `PATCH /me` and writes the answer into the `me` query itself, so a save that lands after the User left still reaches Profile and Cabinet; it runs with `networkMode: "always"`, so offline it fails at once with the offline sentence. A failed save keeps the text and turns Save into Retry. `INVALID_DISPLAY_NAME` shows the matching rule error (`getDisplayNameRefusal`). A save returns to Profile, whose notice line says "Name saved" through the same store as the Sign-in Method lines. Back never asks. Nothing clears the name back to the Generated Name.
- The root Back anchor is `(tabs)`; onboarding is never the first route and no route in its group answers `/`. On launch `resolveOnboardingGate` (`src/onboarding/onboardingGate.ts`) decides within one second, behind the launch entrance, whether this install is owed onboarding: a fresh install is, and anyone with a session or any stored app data is not. A slow or failed read means no onboarding. `OnboardingLaunch` then pushes `/(onboarding)/language` above the tabs, unless the launch came from a deep link. Skip and the last button store the flag and `router.dismissTo(HOME_HREF)`, so the stack is the tabs alone and nothing can go Back to onboarding, including after publishing a Listing. The flow is Language, Find, Chat ([hi-fi spec](../../docs/prd/ui/hifi/mobile-onboarding.md)).
- `src/launch/LaunchEntrance.tsx` owns native release on its first layout and the cold-launch presentation. It matches the native C-dot at 160 pt on #17191D, then reveals the incumbent red wordmark and exact subordinate "By Alpha Motors" credit over 650 ms. The destination mounts when local fonts, locale, saved theme and onboarding settle; the entrance timer controls only presentation. Font/locale/theme read failures do not hold launch indefinitely. Reduced Motion uses a static identity and credit with no presentation delay. Onboarding never releases native itself.
- Home is the Search tab's stack root, `/(tabs)/(search)`. Import `HOME_HREF` from `src/navigation/homeHref.ts` for every "go home" navigation instead of writing the literal.
- Android 12+ tab screens register a `BlurTargetView` through `TabBlurTargets`; the floating bar samples only its focused screen. Older Android keeps the tuned material, Reduce Transparency uses the opaque surface, and iOS retains system glass. A tab mounted on its first visit registers after it is focused; until then the bar keeps the last registered target. Tab taps and slide crossings use native selection feedback, with Reduce Motion on as well. `expo-haptics` adds `android.permission.VIBRATE` to the merged Android manifest through its own manifest; it is a normal permission with no prompt, the selected feedback does not need it, and it is not in `blockedPermissions`. Expo Blur and Haptics require a rebuilt development client; emulator checks cannot prove physical haptic feel.
- The locked five-tab navigation and Auto.ru structural discovery reference follow [ADR-0051](../../docs/adr/0051-auto-ru-inspired-mobile-discovery-before-google-play-review.md). Read the affected approved screen specification before UI work. Do not treat an old Kolesa reference as authority for discovery.
- Chat sockets complement HTTP state. Push uses native FCM/APNS tokens; provider setup and device delivery require runtime evidence, not just passing hook tests. While a User is signed in, `usePushTokenSync` (mounted in the root layout) registers the native token on launch and on return to the foreground, skipping the POST when the server already holds the current token and re-registering when it rotated; it never prompts. `getNativePushToken` never swallows a failure: a rejected fetch (no Google Play services, unreachable FCM) or an empty token is logged with the `[pushToken]` tag and returned as a discriminated result, and the next sync retries, so chat stays fully usable on devices where push cannot work. The one-shot permission prompt still fires only from the first chat action.
- Cabinet's Notifications screen (`/notifications`, signed in only) states the device notification permission (`granted` is On; anything else is Off) and links to the app's system settings. It re-reads the permission on focus and on return to the foreground, never prompts for it, and has no category switches; the prompt stays after the first chat action.

## Native verification

Read [mobile/Expo checks](../../docs/agents/mobile-expo.md) before packages, Metro, navigation, or runtime changes. Keep `shamefullyHoist` in `pnpm-workspace.yaml` and explicit native dependencies. Expo Go cannot run the full app's push integration; runtime verification uses a development build. Preserve store permission restrictions and bundled native/JS release configuration rather than silently introducing an update channel.

The merged Android manifest carries `android.permission.VIBRATE` through `expo-haptics`' own manifest; it is a normal permission with no prompt, the Sign-in Method selection tick does not need it, and it is not in `blockedPermissions`.

For listing media, preserve client compression and staging safeguards in the local overview. New screens must retain localized copy, accessibility, loading/empty/error states, and theme behavior. Do not copy route inventories or old bug plans into this file.

Component tests use a test-only native host adapter with real i18n and Query
providers. See the [mobile testing guide](../../docs/agents/mobile-testing.md)
for supported queries, shared helpers and native runtime limitations.

Listing, chat and Profile Photo uploads encode WebP within the existing 2400 px long-side and 5 MB limits. Profile Photos keep their square crop. Clients request `image/webp` and build `.webp` derivative URLs; detail/fullscreen derivatives preserve natural proportions under [ADR-0096](../../docs/adr/0096-webp-only-photos.md).

The Cabinet business row opens `/business`, whose actual API hooks and localized feature UI live in `src/business`. It accepts a recipient-bound invitation and shows current Owner/Sales membership, protected recovery and owner settings/member/invitation actions. Identity changes hide the previous account's workspace; personal inventory stays separate. Inventory and enquiry workflows consume the current business principal in their own features.

Anonymous [showrooms](src/business/ShowroomScreen.tsx) read the public whitelist projection, refresh on focus, and open existing Listing detail for contact. Public identity and inventory are separate from the authenticated business workspace and enquiry inbox. Sharing activation and installed HTTPS association acceptance remain deployment prerequisites.
