# Background worker

The worker consumes queued work outside the API request path. Native direct-message push, sign-in email, expired-account purge and retired upload cleanup have implementations. Video V1 has a durable PostgreSQL processing ledger, Redis outbox reconciliation and dedicated exact-inventory cleanup. The private-bucket adapter downloads prepared bytes; FFmpeg validates the complete source, creates adaptive HLS and a cropped poster, and adoption checks current target/revision/lease before changing the canonical pointer. Expiry, cancellation and personal-account purge retain cleanup authority and processor/write grace; business stock survives creator purge. Processing and cleanup flags remain closed by default. The pinned FFmpeg/ffprobe Dockerfile and hosted service tests establish source/CI behavior; deployed storage, native end-to-end acceptance and rollout activation remain separate gates. Broad orphan cleanup remains unimplemented and its processor rejects jobs visibly. Failed-job retention follows producer options; inspect failures before requeueing work.

The API owns push eligibility and history creation. For business enquiries the worker also reloads current business, recipient status, membership and assignment immediately before each provider attempt, including retries. Revoked or reassigned staff receive no queued business content. Personal notification policy stays in the API. The worker delivers per token and updates delivery outcomes. Android uses FCM and iOS uses direct APNS behind the push port; preserve invalid-token classification and retry behavior. Provider code existing in Git does not prove deployed credentials or real-device delivery.

Sign-in email uses Resend behind the email port and daily-send cap. Keep credential material and codes out of error/log payloads. Account purge is distinct from broad media orphan cleanup; do not remove its scheduler or privacy-preserving deletion behavior while cleaning scaffolds. The purge job is also the retention job for Sign-in Code records: at purge it deletes the User's `otp_requests` rows (theirs by User id, and signed-out requests to their phone or email) and clears `contactPhone` on the personal Listings it keeps, and on every daily run, even when a purge fails, it deletes every `otp_requests` row older than 30 days. The privacy policy states those 30 days. Business-owned Listings, drafts, adopted media and the business contact remain after creator purge; the retained anonymized User row preserves creator foreign keys. The purge also removes the User's Profile Photo: in the purge transaction, after taking the User row lock, one statement retires the photo's upload and records its deletion work, due at the purge's time, before the User row's photo link is cleared. That statement repeats the API claim's retirement because the purge runs here; a change to how the API retires an upload must be made in both places. The sweep below then deletes the bytes.

Retired upload cleanup ([ADR-0088](../../docs/adr/0088-exclusive-upload-adoption-and-retirement.md)) is not the broad orphan sweep, which stays unimplemented. The API retires an upload and records work in `media_upload_cleanups`; a scheduler on the `retired-upload-cleanup` queue runs one bounded sweep a minute. A sweep first recovers preparations stranded past their deadline. Under [ADR-0089](../../docs/adr/0089-transient-publish-failure-releases-photos.md), an expired publish claim returns to `AVAILABLE` without cleanup: its new Listing id does not exist yet. Attach to an existing Listing and Profile Photo preparations remain terminal. The upload row lock and live link/key checks protect committed or retained media from either recovery action. The sweep then takes due `PENDING` work. It deletes only a fenced (`conditional-v1`) upload's exact manifest, either the five-object WebP set (WebP original and four WebP variants) or the unchanged historical nine-object set (original plus JPEG and WebP of each variant), inside its own `pending/<UUID v4>/` directory, and only while the upload is retired and no Listing media key, poster or Profile Photo key remains under that directory; the worker repeats that rule itself and does not trust the recorded row. Work is marked done only after every key answers HEAD with "not found". The store deletes nothing unless bucket versioning is off, and fails when it cannot read that state, because a delete on a versioned bucket keeps the bytes. Attempts, the next attempt time and the last failure are saved in Postgres before any deletion starts, so retries survive failures and restarts; BullMQ only triggers sweeps. `LEGACY_PENDING` work is never taken, so legacy bytes stay. It uses the worker's existing `MINIO_*` settings and the `listing-photos` bucket. A green suite proves this against the CI MinIO only: the deployed provider's conditional-write and versioning behaviour is a release check a person runs.

Listing-view fingerprint retention ([ADR-0105](../../docs/adr/0105-listing-views-once-per-ashgabat-day.md), #899) has its own `listing-view-retention` queue. Stable scheduler `listing-view-retention-minute` triggers every minute, with a coalesced startup catch-up and three attempts. `ExpireListingViewFingerprints` deletes only `listing_view_fingerprints.expiresAt <= now`, in up to100 batches of1000 with a30s budget and bounded PostgreSQL statements. It leaves daily/lifetime counts and Listing.updatedAt alone. The API's immutable expiry reserves five minutes before48h from the earliest daily signal. Queue/sweep delays must fit that margin; outages/backlog are visible retention failures. Aggregate logs report last success, oldest due timestamp and health, never a fingerprint, Listing id or viewer data. Missing success for five minutes also requires an operational alert. No new worker secret/config is needed. [Issue899 evidence](../../docs/evidence/issue-899/verification.md) owns exact UTC/Ashgabat boundaries, hosted service tests and the remaining deployed acceptance gate.

Read the queue processors and their tests for payload/retry behavior. Environment validation controls the transport; test/unconfigured transports are not production delivery evidence.

Diagnostic work in `src/jobs/diagnostics` renders immutable releases to TK/RU/EN PDFs using embedded licensed fonts and verifies exact private-storage bytes before readiness. Database intents, bounded leases, epochs and retry state survive restarts. Cleanup fences late writes and removes only the recorded object, with readback verification. Account erasure composes `src/jobs/diagnosticAccountErasure.ts` before mutable intake is unlinked. API authorization controls every document/evidence read; successful rendering does not activate a center or public service. [Renderer evidence](../../docs/evidence/issue-916/renderer.md) distinguishes sample/PDF inspection from deployed and native acceptance.

Operational monitoring runs in the separate watchdog entrypoint. Alerts default closed and choose either the existing HTTP sink or the restricted Gmail SMTP adapter. SMTP uses verified implicit TLS, a fixed monitoring recipient, an absolute deadline and its own bounded Redis transition receipt. It does not share the sign-in email driver.
