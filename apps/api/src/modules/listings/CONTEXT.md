# Listings

Listings owns listing lifecycle, drafts, media associations, favorites, discovery reads, and listing-contact verification. Its source and tests define allowed state transitions and edit restrictions. Product scope comes from the owning Listings and Search specifications.

A Verified Contact Phone is independent of a User's Sign-in Methods. Preserve verification and publish gates instead of inferring contact eligibility from the identity phone. Owner mutations and public reads have different visibility and suspension rules. Banned listings cannot be restored through ordinary owner transitions.

Contact phones follow [ADR-0081](../../../../../docs/adr/0081-contact-phone-confirmation-api-for-listings.md). A number may go on a Listing when it is the seller's own sign-in phone (identity's yes/no `holdsSignInPhone`, bound as `ACCOUNT_PHONE_PORT`; Listings never reads the value) or a `verified_contact_phones` row of that seller still inside its 7 days. [`VerifiedContactPhone.isReusableAt`](domain/VerifiedContactPhone.ts) is the only place with the 7-day arithmetic, and [`ContactPhonePolicy`](domain/ContactPhonePolicy.ts) is the one check, returning account, confirmed, missing, not confirmed or expired. Publish and republish require a usable number (`CONTACT_PHONE_REQUIRED`, `CONTACT_PHONE_NOT_CONFIRMED` with `details.reason` `not_confirmed` or `expired`) even when calls are off; republish checks the stored number and takes no body. Edit checks only a patch that changes `contactPhone`, so every other edit, `allowCalls` and `allowChat` included, keeps the stored number past its 7 days, or keeps none on a Listing whose number was cleared. A failed check writes nothing. `ContactPhonesController` serves `/api/v1/me/contact-phones` (`POST request`, `POST verify`, `GET`), refusing suspended Users itself and pending deletions through the global guard. Codes come only through identity's `CONTACT_PHONE_CODE_PORT`, whose purpose Listings cannot choose, and its errors map through `contactPhoneCodeException`. Two sellers may confirm one number, and a confirmation never changes `User.phone`. The day-30 purge deletes a User's rows. It also clears `contactPhone` on the Listings it keeps, so an archived Listing of a purged User has none. Draft payloads still accept any string; the data migration `clear_unverified_listing_contact_phones` cleared stored numbers that were neither the seller's sign-in phone nor confirmed.

Listing detail exposes the auto-numbered public ID and the seller's public identity (`displayName`, `nameNumber`, `avatarIndex`, `avatarKey`, `deleted`) and join date through `SellerProfilePort`, backed by identity's exported `SELLER_PROFILE_READ_PORT`. Public feed items (`GET /api/v1/listings`, Home and Results) also carry what the Results card needs: `allowCalls`, `allowChat`, the first eight photo keys in `galleryKeys` beside the two in `photoKeys` (kept at two for installed builds), and a `seller` with only `displayName`, `nameNumber` and `deleted`. The sellers come from `SellerProfilePort.getCardSellers`, backed by identity's `findUsersByIds`, and the photos from one bounded window query in `PrismaListingsReadRepository.getCardPhotos` (cover, first eight photos and the photo total per Listing); both are one read per page, never per Listing. No feed item carries the contact phone: a caller reads it from Listing detail, which keeps bulk scraping off the list endpoint. The four fields live on the feed-only `FeedListingSummarySchema`, not on the shared `ListingSummarySchema`, so Favorites and My listings summaries carry no seller or gallery; favorites keep `contactPhone`, `allowCalls` and `allowChat`. Under ADR-0056 no response carries a per-Listing phone-trust signal; every displayed contact number is already verified.

The seller condition disclosure is `{ damaged, knownIssuesText? }` ([ADR-0052](../../../../../docs/adr/0052-seller-condition-disclosure-is-damaged-plus-known-issues.md)). Only a Used Listing needs the answer ([ADR-0080](../../../../../docs/adr/0080-a-new-car-skips-the-damaged-question.md)); `domain/damagedAnswer.ts` holds the rule both publish and edit use. Publish rejects a Used draft without a `damaged` answer as `INVALID_DRAFT_PAYLOAD` with a `conditionDisclosure` field error, and edit rejects any change to a Used Listing that has no answer unless the patch supplies one (`DAMAGED_REQUIRED`). A New Listing stores `damaged: false` when the answer is missing, and publish or edit refuses a damaged New Listing, including an edit that only changes Condition to New, with `DAMAGED_NOT_ALLOWED_FOR_NEW`; a disclosure patch without `damaged` already fails the edit request schema (`VALIDATION_ERROR`). A Listing with no answer (only possible for rows from before the migration) returns no `conditionDisclosure`. A supplied disclosure replaces its optional Known issues text; omitting that text clears it, while omitting the entire disclosure preserves it.

Draft saving and `validate-step` use the seven wizard step names from `WizardSchemas` (`vehicle`, `specs`, `photos`, `price`, `location`, `contact`, `review`); [Mobile listings](../../../../mobile/src/listings/CONTEXT.md) owns the order and the resume rule. `UpdateDraft` keeps only those names in `validatedSteps`, so the eight-step wizard's `vin` name disappears on the next save, and `validate-step` rejects `vin` as a validation error.

Publication, republish and field edits require at least three image media; drafts may hold fewer. Existing low-photo Listings remain readable until a mutation, and attachments can repair them. Removal checks the floor under a Listing row lock before releasing upload provenance, so concurrent removals cannot cross it. The mobile guidance target is eight, and the maximum remains twenty, from shared contract constants.

Media upload staging and server attachment are distinct steps. Preserve ownership checks, image limits, ordering, and variant behavior.

Image presign accepts opt-in `writeProtocol: "conditional-v1"`; the default remains compatible with installed clients. Conditional uploads initialize their fixed original/eight-variant manifest once, return a signed `if-match` PUT header, and preserve that protocol in private upload provenance. Conditional placeholders/originals/variants carry `Cache-Control: no-store`; actual origin deletion does not erase offline/third-party copies. Every conditional original/variant rewrite requires a current ETag; missing issued objects are never recreated. Attach/publish pass the recorded protocol into generation rather than looking it up after removal. Provider capability and unversioned-bucket checks fail closed. Chat retains its independent upload path. [ADR-0088](../../../../../docs/adr/0088-exclusive-upload-adoption-and-retirement.md) explains the storage fence. Legacy writes supply no fenced deletion guarantee.

An upload has one adopter across Listing media and Profile Photos, decided by the common claim ([`UploadClaimPort`](domain/ports/UploadClaimPort.ts), [`PrismaUploadClaims`](infrastructure/PrismaUploadClaims.ts)), not by the two unique relation columns. `media_uploads.state` moves `AVAILABLE`, `PREPARING`, `ADOPTED`, `RETIRED`, `DELETED`, and every step first takes the upload's row lock, in id order. Attach and publish reserve their uploads before classification or Sharp runs, all or none, and finalize in the transaction that writes the association; publication's Listing, media rows, draft removal and audit entry commit with it. A retry for the same Listing joins the reservation in flight and gets the one committed row. A failed preparation is terminal: the upload is retired and the seller presigns again. Any writer that also locks a Listing or User takes that lock first, then uploads. Profile infrastructure (#642) must use the same port with a `profile` target and write `users.avatarUploadId` in the finalizing transaction; nothing does yet.

Retirement is permanent and happens in the transaction that releases the adopter. It records deletion work in `media_upload_cleanups`, which has no foreign key so it outlives the upload and its User. No request deletes stored objects any more: [the worker](../../../../worker/CONTEXT.md) does, for fenced uploads only. A retired legacy upload is recorded as `LEGACY_PENDING` and its bytes stay, so removing a photo an installed client uploaded no longer frees storage. A writer that adds a new reference to an upload's directory without going through the claim breaks the worker's guarantee that no live reference loses storage.

Listing media is authorized by server-recorded upload provenance ([ADR-0079](../../../../../docs/adr/0079-server-recorded-upload-provenance-for-listing-media.md)). Presign records a Media Upload for the calling User. Publish and attach adopt only that User's unadopted upload whose stored object still matches it (`UploadAdoptionGuard`); a known or forged key authorizes nothing, and object keys are public in Listing detail. `listing_media.uploadId` stays unique as a backstop. Removal deletes the row and retires its upload together; a retired or deleted upload answers `UPLOAD_NOT_AVAILABLE` like an unknown key. A duplicate row with no upload retires nothing, and a row whose key is not its upload's key retires nothing. Pre-deploy photos held only in drafts or client queues must be removed and re-added before publication. Retrying an attach on the same Listing returns the existing media row. Unattached uploads and their objects are not swept yet. Database columns alone do not guarantee consistency among every optional catalog ID; inspect the actual validators before claiming a relationship is enforced.

A User keeps at most `MAX_DRAFTS_PER_USER` (5) drafts. `CreateDraft` saves through `ListingDraftRepository.saveWithinLimit`, which locks the owner's `users` row before counting, so concurrent creates cannot exceed the cap; a refusal is `409 DRAFT_LIMIT_REACHED`. Publishing deletes the draft and discarding deletes it, which frees a place. Drafts are never expired or cleaned up automatically.

Ranking/filtering belongs to the existing read adapters. Other contexts use exported read/admin ports. When changing publication, contact, or deletion, inspect conversation and moderation consumers as well as mobile create/edit flows.

Identity infrastructure writes Listing rows directly when a User's account deletion is scheduled or restored. `PrismaAccountDeletionUnitOfWork` archives the seller's active Listings with `archivedByDeletion = true` in the transaction that sets the deletion schedule, and `PrismaAccountRestoreUnitOfWork` republishes only the Listings with that flag in the transaction that clears it. A change to Listing statuses, the `archivedByDeletion` rules or `publishedAt` on republish must check those two adapters first.

Feed price sort and price-range counts read the stored `Listing.priceTmt` ([ADR-0061](../../../../../docs/adr/0061-stored-tmt-listing-price-for-feed-sort-and-range.md)). Publish, edit, and republish write it in the same statement as the Listing; after any `exchange_rates` change an operator must run the recompute (`packages/db` `listing-prices:recompute`). Display prices and the `priceMin`/`priceMax` filter convert at request time, so a stale `priceTmt` mis-orders and mis-counts but never shows a wrong price. The public feed pages in six orders (`newest` default, `price_asc`, `price_desc`, `year_desc`, `year_asc`, `mileage_asc`) with per-order keyset cursors, alongside `GET /api/v1/listings/count` (match count with the TMT price range of the matches) and `GET /api/v1/listings/filter-options/brands` (active-Listing counts per brand).
