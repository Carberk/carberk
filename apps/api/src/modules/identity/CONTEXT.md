# Identity

Identity owns Users, Sign-in Methods, sessions, admin elevation, account deletion, and identity checks consumed by other contexts. Marketplace Role and Dealership Member role are different concepts. Listing contact verification belongs to Listings and cannot authenticate a User.

Sign-in checks the User's current suspension through `IdentityCheckPort` before consuming a code and again before creating a Session. Phone and email Sign-in Codes, reviewer and tester bypass all refuse suspended Users with `USER_SUSPENDED`; presentation maps the shared `UserSuspendedError`. Suspension through `IdentityAdminPort` deletes the User's Sessions in the same moderation transaction. Refresh also refuses a suspended User before rotating a remaining Session. Unsuspension permits new sign-in and never restores revoked Sessions (founder decision in [#749's fix round](https://github.com/bagtyyarkovusov/auto.tm-rewrite/pull/749#issuecomment-6050075951), consistent with ADR-0012).

Refresh tokens are hashed on Session. Refresh rotates in place with a compare-and-swap check so a concurrent retry cannot reuse the old token. Admin TOTP elevation has its own deadline; ordinary refresh preserves it without extending it. Pending TOTP enrollment is idempotent, including concurrent creation, so returning to setup does not invalidate an already scanned secret.

Phone and email code flows share ownership and one-time-consumption rules. Every `otp_requests` row stores its purpose ([ADR-0081](../../../../../docs/adr/0081-contact-phone-confirmation-api-for-listings.md)), and `VerifySignInCode` checks only the newest code of the caller's purpose: sign-in, Sign-in Method change and account deletion each accept only their own codes, and a code of another purpose keeps its attempts. Sign-in and Sign-in Method change answer it with `OTP_NOT_FOUND`; web account deletion answers `INVALID_OTP` for every code failure, so a response never reveals whether a User holds the value ([ADR-0054](../../../../../docs/adr/0054-phone-or-email-sign-in-share-one-user.md)). `listing-contact-phone` codes are issued and checked only by `IssueContactPhoneCode` and `ConfirmContactPhoneCode`, exported to Listings as `CONTACT_PHONE_CODE_PORT` (`requestCode`, `confirmCode`) with the purpose fixed inside identity. They are bound to the requesting seller, never sign anyone in or change a Sign-in Method, and never use the reviewer bypass. A wrong code throws `InvalidSignInCodeError` carrying `attemptsLeft`; `contactPhoneCodeException` (exported) maps it to `INVALID_OTP` with `details.attemptsLeft` and maps the other code and rate-limit failures, while the sign-in, method-change and deletion verify endpoints still answer `INVALID_OTP` without details. The contract `SignInCodePurpose` is stored as the database enum `CodePurpose`; [`codePurpose.ts`](infrastructure/codePurpose.ts) is the only mapping. Sign-in, Sign-in Method change, account deletion and Listing contact-phone issuance all reserve through `OtpRequestRepository.reserve`. Its PostgreSQL transaction takes normalized channel/destination then IP advisory locks in separate two-int namespaces, reads every purpose under READ COMMITTED, checks the rolling 24-hour destination and one-hour IP budgets and cooldown, and inserts before commit. Admission samples the injected clock after both locks and uses it for windows, createdAt and expiry. Lock/transaction waits are bounded; storage and timeout failures remain operational errors. Delivery runs after commit, and a delivery failure leaves the reservation counted. This guarantee requires every serving issuance writer to use the operation; old processes do not participate in its advisory locks. The worker deletes `otp_requests` rows older than 30 days (`PurgeExpiredAccounts`), so a count or backoff window must stay well inside 30 days. Account-deletion codes bind to the holder at request time; do not replace that with an unbound sign-in lookup. Reviewer bypass is narrower than normal authentication and never authorizes deletion or a Sign-in Method change. The same sign-in-only rules apply to temporary testers from `TESTER_ACCOUNTS_JSON` under ADR-0086. Their entries work independently of the reviewer flag, use the same comparison/no-send/audit path, and require pre-existing ordinary Users from the separate operator seed. Reserved reviewer/tester phone verification uses no stored request. With that bypass enabled, wrong fixed codes and codes for absent, admin or moderator Users answer `INVALID_OTP` without an ordinary OTP lookup. Reserved phone verification counts failures per destination in Redis under an identity-owned key prefix, atomically across API instances. Five failures within 15 minutes start a full 15-minute lock from the fifth failure; blocked retries and resends never extend or clear it, and the correct code is refused with the existing `OTP_LOCKED` response until expiry. A successful sign-in resets the failure count. Refused attempts for absent or privileged reserved Users share the same budget so its threshold cannot confirm their code. Only reserved phone sign-ins probe the ledger; an ordinary phone returns before the probe, so ordinary sign-in keeps no Redis dependency and its code limits are unchanged. Reserved User lookup and full-list comparison do not branch on a matching code. A Redis error or slow probe refuses the reserved sign-in with the lock response rather than enabling an unlimited bypass. Reserved email still requires a stored request and retains its five-attempt limit, expiry, issuance limits and consume-once behavior. [ADR-0092](../../../../../docs/adr/0092-temporary-failure-limits-for-fixed-code-phone-sign-in.md) proposes superseding ADR-0030's never-locked-out guarantee for the fixed-code verifier. The reviewer scenario seed still reads only the reviewer list. Inspect the use-cases and integration tests before changing rate limits, verification, or enumeration protection.

A refused Sign-in Code request throws `SignInCodeRateLimitedError`, which carries the `OtpAttemptLedger` reason. The three request endpoints (sign-in, Sign-in Method change, account deletion) answer `RATE_LIMITED` with `details: { reason, retryInSeconds }` (`destination_limit`, `ip_limit` or `backoff`; the wait is nonzero only for `backoff`) so the app can tell "wait a moment" from "no more codes today". The reason comes only from the destination and IP counts and the last attempt, never from whether a User holds the value, and controllers match the error class rather than a message. Keep it that way.

Other modules import identity only through [`identity.public.ts`](identity.public.ts), plus `identity.module.ts` and `profile-photo.module.ts` for Nest composition; `apps/api` lint rejects imports of identity internals or `identity.tokens`. It mirrors the providers `IdentityModule` exports: identity check, contact-phone codes, identity read, identity admin, seller profile read, readonly admin session elevation, and clock. Session records and repository writes stay private to Identity; `AdminGuard` keeps the admin-role policy and maps elevation results to the existing HTTP errors. [`CheckAdminSessionElevation`](application/CheckAdminSessionElevation.ts) checks session ownership before deadlines, using one clock sample after lookup. `IdentityCheckPort.holdsSignInPhone` answers whether a phone is the User's own sign-in phone without returning it.

SMS codes go out synchronously through `OtpSenderPort.send({ phone, code, purpose, locale, requestId })`. [`renderCodeSms`](domain/codeSms.ts) holds the only approved text, the one-segment contact-phone SMS in RU, TK and EN; the other purposes have no wording yet and send the bare code. `HttpOtpSenderAdapter` builds the `apps/sms-gateway` body `{ phone, body, requestId }` but still only logs in both `mock` and `gateway` modes. Its log lines carry only the last four digits of the phone number and nothing else derived from it (no hash: beside the last four digits a digest would pick the number out), because the hosting log outlives the 30-day retention of `otp_requests`; the `mock` line also carries the first eight characters of the request's id, which the caller receives as `requestId` and which tells same-last-four requests apart, and the code, which is how a code is read where no SMS is sent (PR backends, staging, and the reviewer-production signup probe). `gateway` mode never logs the code.

Every User carries a Generated Name number (`nameNumber`, 1000 to 9999) and an Assigned Avatar index (`avatarIndex`, 0 to 11), drawn once at creation and never changed; neither is unique. `VerifyOtp` draws them with [`drawGeneratedIdentity`](domain/GeneratedIdentity.ts) from `RANDOM_SOURCE_PORT` and passes them to `UserRepository.create`. The database holds the same ranges as check constraints and as a random column default, which also numbered the Users that existed before the column. The server stores the number, not the text: `displayName` stays null until the User sets a name, and readers build the Display Name with `formatDisplayName` from `@auto-tm/contracts`, prefixed in their own language. `/me`, the Sign-in Method confirm and `POST /me/restore` return `nameNumber`, `avatarIndex` and `avatarKey` (null when the User has no Profile Photo); the sign-in verify payload does not. The day-30 purge clears `displayName` and the Profile Photo and keeps the number and index, which identify nobody. `avatarUrl` is unused and stays null.

A User may hold one Profile Photo ([ADR-0088](../../../../../docs/adr/0088-exclusive-upload-adoption-and-retirement.md)). `PUT /api/v1/me/photo` (`SetProfilePhoto`) takes the key of an image the User presigned through the Listing upload route with `writeProtocol: "conditional-v1"`, and `DELETE /api/v1/me/photo` (`RemoveProfilePhoto`) clears it; both answer with `/me`, never change `avatarIndex`, and refuse a suspended User and a pending deletion like `PATCH /me`. Sending the current key again changes nothing, a second photo replaces the first, and removing with no photo succeeds. Identity code knows uploads only as [`ProfilePhotoPort`](domain/ports/ProfilePhotoPort.ts) (`adopt`, `release`): ownership, the stored-object check, metadata stripping, variants, the one-adopter claim and the storage deletion record all stay in Listings, which implements the port, and refusals (`ProfilePhotoErrorCode` in contracts, the Listing upload codes) pass through unchanged. `ListingsModule` imports `IdentityModule`, so the two photo routes and use-cases are composed in [`profile-photo.module.ts`](profile-photo.module.ts), above both; it is the only identity file that names Listings, and lint rejects any other such import. The Listings adapter writes `users.avatarUploadId` and `users.avatarKey` itself, under the User row lock, in the transaction that finalizes or retires the upload; `avatarUploadId` is private and no read port returns it. Nothing else may write those two columns: a write that skips the port leaves an upload adopted with no photo, or deletes a photo's storage while it is still shown. A moderator removes a photo through Admin (`POST /api/v1/admin/users/:id/remove-photo`), which calls `release` inside its own transaction. The purge runs in the worker and repeats the retirement there.

`PATCH /api/v1/me` (`UpdateDisplayName`) sets the User's own Display Name and answers with `/me`; it is the only field the route changes, and other body fields are dropped. The rule lives once in `@auto-tm/contracts` (`normalizeDisplayName`, `displayNameProblem`), shared with the app: control characters other than whitespace dropped (PostgreSQL text cannot hold NUL), ends trimmed, whitespace runs collapsed, 2 to 30 code points, any script. [`DisplayName`](domain/DisplayName.ts) applies it; a refusal is 400 `INVALID_DISPLAY_NAME` with `details.reason` `empty`, `too_short` or `too_long`, and its message never carries the name. Names are not unique or moderated, and there is no way back to the Generated Name yet. A suspended User is refused with 403 `FORBIDDEN` and `details.reason` `USER_SUSPENDED`, as on Listings mutations; a pending deletion is refused by the guard below.

Other Users see a User's **public identity** (`domain/ports/PublicIdentity.ts`): `displayName` (null until set), `nameNumber`, `avatarIndex`, `avatarKey`, and `deleted`, true for a User purged after deletion (no Sign-in Method left). The exported `SELLER_PROFILE_READ_PORT` gives other contexts a seller's public identity and join date from `User.createdAt`, and the identity read port's summaries carry the same fields. Both adapters build them with `infrastructure/publicIdentityRow.ts`, which reads phone and email only to derive `deleted`; neither port exposes Sign-in Method values, verification state or upload ids.

The identity read port answers lists in one read per question: `findUsersByIds` for public identities and `findBlockedUserIds` for which of a set of Users a blocker has blocked. Callers use them instead of one `findUserById` or `isUserBlockedBy` call per row. Neither returns Sign-in Method values.

Suspension blocks marketplace mutations while preserving permitted reads and account deletion. Deletion has a grace period followed by worker purge; inspect both sides and database history-retention rules before changing the lifecycle. `DeleteMe` (behind `DELETE /me` and the public deletion confirm) first revokes the User's refresh sessions through the session repository, then sets the schedule and archives the seller's active Listings in one transaction (`AccountDeletionUnitOfWork`, implemented by `PrismaAccountDeletionUnitOfWork`). Refresh state stays out of that transaction so only the session repository writes it. Every failure therefore leaves the User unscheduled and the deletion retryable (`DELETE /me` again, or on the web a new code, since the first code is spent before `DeleteMe` runs); once the schedule is set, the pending-deletion guard below refuses a repeat.

Restoring a User in the grace period is a separate, confirmed step. Verifying a code (normal or reviewer path) signs the User in and answers `user.deletionScheduledAt` without clearing the schedule or republishing Listings. Only `POST /api/v1/me/restore` (`RecoverAccount`) clears the schedule and republishes the Listings the deletion archived; it answers with `/me` and is idempotent for a User with no scheduled deletion. Until then the session cannot change marketplace data: `AccountDeletionPendingGuard` (global, registered after `JwtAuthGuard` and `ThrottlerGuard`; `app.module.spec.ts` locks the order) answers any signed-in non-read request with 403 `details.reason = ACCOUNT_DELETION_PENDING`, except public routes and routes marked `@AllowPendingDeletion()` (restore, logout-all; logout is public). Realtime events skip HTTP guards, so the Conversations use cases they reach (message send, delete, and watermark updates) call `ConversationAccessPolicy.assertAccountNotPendingDeletion`. Both answers come from `accountDeletionPendingException()`, exported by `identity.public`. A pending session can still read, including `GET /conversations/:id`, whose `sendRestriction` has no value for a pending deletion. The app never stores the session from a pending sign-in, but a session stored earlier on another device keeps a valid access token for up to 15 minutes (`JWT_ACCESS_TTL`) after the deletion is requested elsewhere, because deletion revokes only the refresh sessions. That device can read `sendRestriction: null` while its sends are refused by the guard and by `ConversationSendPolicy.authorize`; a new `sendRestriction` value needs a contract decision. A new mutating path that bypasses HTTP, such as another socket event, must call the same check. `RecoverAccount` republishes the Listings and clears the schedule in one transaction (`AccountRestoreUnitOfWork`, implemented by `PrismaAccountRestoreUnitOfWork`), so a failed restore changes neither and stays retryable.

Staff authority is purpose-scoped and separate from marketplace roles and Dealership membership. Other contexts use `STAFF_AUTHORITY_PORT` from [identity.public](identity.public.ts) or the HTTP [StaffGuard](../../common/staff.guard.ts). Each authorization reloads the actual Session and current User/grants, rejects suspended/deleting Users, and requires unexpired session and TOTP elevation. Feature owners still enforce assignment, audience and reason/audit for restricted reads, sockets, files and exports; possession of a capability alone never supplies those policies. `summary` permits setup before elevation and exposes only current named capabilities and the existing elevation deadline. Admin TOTP routes retain their released response shape and also accept explicitly granted scoped staff through `/auth/staff/totp`; marketplace admin access remains under its existing AdminGuard.

[Staff grant transitions](infrastructure/PrismaStaffAuthority.ts) require explicit elevated `staff.manage`, lock the actor/target and current Session, and write the named actor/target/reason audit in the same transaction. Founder-controlled grants additionally require `founder.control`; it cannot be granted from HTTP. Admin role grants no implicit staff management or private purpose. [The explicit bootstrap operator command](../../../../../packages/db/scripts/bootstrap-staff.ts) provisions an exact verified active User/capability with reason, dry-run and atomic audit; it is never a migration, seed or API fallback. No live onboarding is performed by delivery. Staff shares existing personal sign-in, TOTP secret, backup codes/throttling and twelve-hour Session elevation. Grant revocation is checked per request even while a token remains valid. Account deletion's Session revocation and current deletion status deny existing staff access. Scheduling deletion also revokes staff grants with durable audit in the deletion transaction; restoration never silently reactivates those grants.

Business admission, membership, invitation redemption and protected owner recovery live in `PrismaBusinessRepository`, composed by the individual business use-cases and `BusinessController`. Admission/recovery require current elevated `founder.admission`/`founder.recovery` staff capability. Owner/Sales membership never grants staff capability. The existing Dealership tables hold the business; invitations store only hashed single-use recipient-bound tokens. Account deletion detaches membership and leaves ownerless business operation in protected recovery without automatically promoting Sales.

Other contexts consume only `BUSINESS_AUTHORITY_PORT` from `identity.public.ts`. Context selection is explicit: omitted business ID means personal. The port reloads the current Session, User, membership and business on every call; inactive Users/members have no business access. Inactive business operation is refused while explicitly requested authorized history remains readable. Consumers must perform their own resource ownership and purpose checks; this port does not move personal inventory or grant private staff access.

The email enqueue adapter uses the shared database campaign fence only for reservation-owned `campaign897.invalid` destinations. An exact journaled request and active namespace are required; cleaning, disposed, missing or foreign ownership refuses enqueue. This adds no authentication bypass. [Shared staging controls](../../../../../docs/agents/shared-staging-controls.md) own preparation, cleanup and deployment gates.

Campaign queue adds use `campaign-${namespace}-${requestId}` deduplication without expiry. Cleanup permanently fences those exact Redis keys with reservation/candidate/request tombstones before removing jobs, preserving safety if an admitted producer outlives its SQL transaction. Ordinary email queue options are unchanged.
