# Database

The schema, migration history, generated-client boundary, and seed inputs live here. Inspect `schema.prisma` for fields and relations instead of copying them into documentation. Runtime consumers load the compiled package. [The source capture adapter](src/measurement-capture.ts) is shared by API and worker source transactions, preserving collector authority, savepoint isolation and latency budgets without importing either application.

`Listing.publicNumber` is a unique, database-assigned integer for the public detail footer. Its migration numbers existing Listings; subsequent inserts take the next sequence value. UUIDs remain the internal identity and route key.

`users.nameNumber` (1000 to 9999) and `users.avatarIndex` (0 to 11) have random column defaults and range check constraints that Prisma cannot express; `schema.prisma` mirrors the defaults as `dbgenerated` in PostgreSQL's own rendering, so `prisma migrate diff` stays empty. The defaults numbered existing Users when the columns were added and let an older API still create Users; the API normally draws both values itself.

`listings.damaged` is the seller's "Damaged / needs repair" answer (ADR-0052). It is nullable only so its migration applies to existing rows; the API requires it, and the fixture and reviewer seeds set it on every Listing. The earlier accident, mileage-accurate, owner-count, and service-history columns were dropped without data migration, so environments are reseeded.

The Lugong/LiuGong correction migration moves the 12 legacy CLG aliases from Shandong Lugong to LiuGong. It preserves Listing content, Generation IDs and draft payloads, reuses an existing LiuGong Model when present, and retains a moved Model ID otherwise. It stops before any change if an affected SavedSearch exists, including a brand-only Lugong or LiuGong search, because changing the matched manufacturer set needs an explicit meaning-preserving correction. The seed keeps the ten actual Lugong models and identifies the existing `john` Brand as John Deere without changing its ID or slug.

`Brand.logoKey` is a nullable object key in the `catalog-assets` bucket (see the catalog overview for the layout). Null means no logo.

Brand logos are filled by an operator script, not by a seed. `prisma/seed/brand-logos.manifest.json` lists every catalog brand once, with a tier (A to F, from the logo research) and either a source or a reason there is none. The manifest validates source provenance, image format, safe master paths and checksums. Recorded license categories do not determine coverage. Simple Icons stays version-pinned and existing Commons sources stay checksum-pinned. Additional manufacturer artwork, category illustrations and explicitly identified full-name labels are bundled under `prisma/seed/brand-logo-masters`; the manifest pins the cleaned master and records its upstream source/hash and normalization. Supported master formats are SVG, PNG, JPEG and WebP. Sourced entries allow safe lowercase Unicode catalog slugs; the API URL-encodes every key segment. Bundled files are loaded only from the pinned directory, with symlinks escaping it refused. Commons downloads remain operator-side and cached; the API, worker and mobile app never fetch external logo sources.

`pnpm --filter @auto-tm/db logos:import [-- --dry-run] [-- --force]` needs `DATABASE_URL` and the `MINIO_*` variables of the target environment. It renders each master to black-on-transparent PNG masks at 30, 60 and 90 px, uploads them to `catalog-assets`, sets `Brand.logoKey`, and prints coverage by tier. A second run changes nothing. It never overwrites a logo an admin uploaded unless `--force` is given: ownership is read from the stored key, so an `imp-<hash>` or `imp-<hash>-<uuid>` directory is an import even after a brand rename, and any other key is treated as an admin's. Every new activation writes a directory that has never been active (`imp-<hash12>-<randomUUID>`), so a delayed admin cleanup of an earlier directory cannot delete it ([ADR-0072](../../docs/adr/0072-imported-logo-cleanup-coordination.md)). `imp-<hash12>` is only the content/render identity: when the active key already has that identity the script repairs missing objects in that exact stored directory and never writes `Brand.logoKey`. Before each activation it re-reads the brand by id, rejects a renamed brand, and swaps the key only if both slug and key are unchanged. Previous imported versions and uploads from a failed compare-and-swap are retained; the script does not garbage-collect imports. Forced replacement deletes the previous admin directory in batches of at most 1,000 keys and reports deletion failures. Old deterministic importer processes must be stopped before API whole-prefix deletion is enabled. Running it against staging or production is an operator step. Curating the manifest, and the object layout, are described in the catalog overview.

Conditional image uploads use `media_uploads_conditional_manifest_check` to accept five-object WebP-only manifests and existing nine-object manifests. The check retains the image kind and original-key membership requirements; the protocol allowlist remains separate. This cardinality expansion leaves upload rows, adopters and cleanup records unchanged. Exact manifest and UUID-prefix ownership checks belong to the application and worker, so passing the SQL check alone grants no deletion authority.

Cross-context foreign keys are allowed; application use-cases still use ports for cross-context access. Database integrity does not waive the application boundary. Keep schema changes with their committed migration, use forward corrective migrations, and reserve `db push` for localhost. The API pre-deploy step is the sole deployed migration authority under ADR-0039.

Deletion intentionally preserves some history while erasing or nulling personal data. Check identity deletion, worker purge, and migration tests before changing cascades, nullable audit actors, or retained messages. Seeds and reviewer scenarios have separate purposes; do not run operational scripts against a live database as a cleanup check. Keep credential values out of seed/audit evidence.

The demo inventory for reviewer production (`scripts/demo-inventory.ts`, `--mode seed|remove`, [runbook](../../docs/prd/ops/80-deployment-runbook.md#demo-inventory-seed-and-removal)) owns exactly the rows reachable from one marker, defined in `scripts/demo-inventory/marker.ts`: the Users whose id starts with `de300703-0000-4000-8000-`. Those are the demo sellers (`…-0000…`). Their Listings (`…-0001…`) and media rows (`…-0002…`) have ids in the same namespace, and every stored photo sits under `demo-inventory/` in `listing-photos`. Removal also deletes the photos sent in Conversations about demo Listings, under `chat-attachments/<conversation id>/` in `chat-attachments`. Removal starts from the marker and never matches by content, so do not create any other row in that id namespace or any other object under that key prefix. A demo seller's only Sign-in Method is a phone tombstone, `demo-inventory:<user id>`, which the API never accepts for a sign-in code; without it every reader would treat the seller as a deleted User. The seed writes no audit row. `scripts/demo-inventory/photos.manifest.json` is the licensing record for the photographs (Wikimedia Commons only, author and licence per file); no photo bytes are committed, and the web credits page is generated from it with `pnpm --filter @auto-tm/db demo-inventory:credits`.

`listings.priceTmt` is a stored TMT price derived from `priceAmount` and the `<currency> -> TMT` rate; feed price sort and price-range counts read it ([ADR-0061](../../docs/adr/0061-stored-tmt-listing-price-for-feed-sort-and-range.md)). The conversion expression is shared between `src/listing-prices.ts` (`recomputeListingPricesTmt`) and the `20260928000000_add_listing_price_tmt` backfill — keep them identical. After any `exchange_rates` change, run `pnpm --filter @auto-tm/db listing-prices:recompute` against that environment's database.


Temporary tester provisioning and removal live in `scripts/tester-accounts.ts`, under ADR-0086. The seed owns only Users whose deterministic ids start with `de300712-0000-4000-8000-`, separate from demo inventory and reviewer scenarios. It refuses to claim existing unrelated phone/email holders, or privileged Users. Removal preflights ownership, schedules deletion now, revokes Sessions and archives active Listings atomically for the existing worker purge. Keep the original secret list until removal; the script refuses changed Sign-in Methods and never reseeds a scheduled or purged User. See the deployment runbook's Tester accounts section. Never create unrelated Users in that id namespace.

The [campaign email fence](src/campaign-email-delivery.ts) serializes API enqueue and worker staging mock delivery with reservation cleanup. It reads the fixed operational namespace journal rather than creating authentication records. Missing journals and cleaning/disposed namespaces refuse delivery. The [fixed fixture program](../../scripts/staging-campaign.mjs) owns that operational schema and terminal metadata, separate from application migrations. Protected mock content is removed only after exact BullMQ disposition; activation still requires hosted and deployed acceptance.

The seed `_legacy/cars.brands.json` is retained as the source snapshot for the S3 brand/model import recorded in the locked [catalog sprint](../../docs/prd/sprints/sprint-03-catalog.md). It is provenance, not a runtime seed input; read it only when investigating that import.

The Railway native-session demo data (buckets, reference data, UI fixtures and licensed logos) is prepared by `scripts/native-pr-seed.mjs`. Its only mode is `--remote`, run over Railway SSH inside the PR API container on private service connections: `node /app/scripts/native-pr-seed.mjs --remote`. It accepts only AutoTM PR environment names and mock SMS and rejects production. The root `pnpm native:seed` script points at the same entry point but, with no arguments, refuses: local (non-remote) mode was removed because it could not be bound to the PR environment's database. The entry point and the `ui:fixture` script's `--railway-pr` step share one pure guard, `packages/db/scripts/native-pr-seed-guard.cjs`, tested from `scripts/native-pr-seed.test.mjs`. See [the agent procedure](../../docs/agents/mobile-expo.md#shared-staging-native-sessions). The ordinary `ui:fixture` command remains localhost-only.

The fixed reviewer scenario uses three bundled licensed Camry photographs per Listing, under `scripts/reviewer-fixtures/`, with source and licence records alongside the files. The seed re-encodes original and resized WebP objects without EXIF/GPS and upserts fixed media IDs. It uses only local photo bytes, preserves the reviewer catalogue namespace and fixed Listing IDs, and leaves media intact in revoke mode. Its synthetic catalogue display names identify Toyota Camry Hybrid demo vehicles; public attribution shares the demo credits page. The operator supplies MinIO credentials and runs seed or revoke against the intended environment.

The [WebP photo converter](scripts/convert-photos-webp.md) inventories both photo buckets and selected photo-bearing scalar/JSON/manifest columns. It preserves identities, journals conditional object writes, uses row-lock compare-and-swap transactions, verifies replacements and references, and separates JPEG deletion from apply. MinIO ignores `If-Match` on DeleteObject, so each delete PUTs an `If-Match` tombstone at the planned ETag (412 refuses a changed object), journals it, deletes it plainly and reads back that the key is gone. Only the writer pause protects the key between those steps. It preserves immutable AuditLog snapshots and completed upload/cleanup history. Proven expired unadopted placeholders retire through the existing cleanup ledger before a fresh inventory; adopted/referenced empty photos fail closed. It requires the API/worker maintenance startup pause, stopped prior instances and 600-second presign expiry before apply and again before deletion. Regenerated derivatives use a shared URL cache version without changing storage ownership keys. It never reseeds either environment.

The [ThumbHash backfill](scripts/backfill-thumbhashes.md) (#824) fills the ThumbHash of every image `ListingMedia` row and live image Message that has none, from its stored WebP original, with the API's encoding. It then fills a Listing-reference Message's `coverThumbHash` from its Listing's hashed cover photo. A row deleted during the run is skipped, not reported. Its dry-run, apply and verify modes are idempotent: they write only null hashes, through conditional updates. It refuses while any live JPEG reference or JPEG object remains, so it runs only after the converter's `verify` and `delete-jpeg`.

Explicit purpose staff grants are additive to marketplace roles. The [staff bootstrap](scripts/bootstrap-staff.ts) is an operator-only command requiring an exact active verified User ID, allowlisted capability and reason; `--dry-run` writes nothing. It writes a system bootstrap audit atomically with the grant, including founder control, without changing marketplace role. Normal grant/revoke transitions belong to Identity's current-authority API, not seeds or migrations.

The [reserved staging controls](../../docs/agents/shared-staging-controls.md) own a narrow synthetic seller/Listing fixture, exact original snapshots and guarded cleanup. They preserve the broad native PR seed's staging refusal. The default-closed campaign identity prerequisite profile tracks reservation-owned auth and delivery records. Guarded reset fences exact journaled OTP queue jobs with permanent deduplication tombstones, removes owned inactive jobs and mock sink content, and retains retryable ownership when active jobs or foreign values prevent cleanup. The hosted disposable PostgreSQL/Redis lane verifies this bounded cleanup; [fixture evidence](../../docs/evidence/campaign897-fixtures/verification.md) records profile scope and operational gates. Broader campaign graph cleanup and deployed/native acceptance remain pending; live staging activation requires separate reviewed identity, reservation and restoration evidence.

The serialized campaign storage program also recognizes an explicitly selected `campaign897-full-v3` bootstrap. It reuses the fixed fifteen-identity media-free business journal and exact baseline reset with manifest version 3. This partial profile admits only reservation-owned sign-in OTP journaling, exact delivery ownership, the one-time binding of a consumed code to its roster User, normally generated Sessions of roster Users, and normal staff TOTP: one pending enrollment per roster User, its single first verification with ten single-use backup codes, and elevation of an existing live Session of a User with an active grant and that verified enrollment. No Session is created elevated, and TOTP reset or re-enrollment stays refused. It also admits ordinary staff grant and revoke transitions of the fixed capability contract (never `founder.control`) to a roster User. Each transition must carry exactly one owned grant audit from a different roster User who currently holds staff.manage, plus founder.control where policy requires it, and who has an elevated live Session. The coordinator's two bootstrap grants stay fixed, and reset redacts and retains every owned audit. Reset commits the cleaning fence before exact delivery disposal, then removes protected sink content and the recorded backup codes, enrollments, Sessions and OTPs, in that order, under the cleanup locks; terminal retries observe retained proof without recreating it. Bounded delivery disposal has hosted verification. Hosted runs reached TOTP enrollment and elevation; grant transitions and secret-row disposal await it. See the [delivery disposal](../../docs/evidence/issue-901/full-v3-delivery-disposal-source-20261020.md), [staff TOTP](../../docs/evidence/issue-901/full-v3-staff-totp-source-20261020.md) and [staff grants](../../docs/evidence/issue-901/full-v3-staff-grants-source-20261020.md) handoffs. It admits ordinary synthetic business admission only. A Dealership created in the same transaction is adopted through its roster owner invitation and exact `BUSINESS_ADMITTED` audit, using a transaction-local creation slot that is not a security boundary against same-role SQL ([admission source](../../docs/evidence/issue-901/full-v3-admission-create-source-20261020.md)). Admitted rows reset exactly with the audit redacted and retained. Redemption, settings, recovery, the shared-baseline guard and the remaining full-release graph stay closed. The operator CLI, controller and Railway profile allowlists remain closed to v3.

`admin:promote` selects an existing phone holder or a unique verified canonical email holder and commits role plus contact-free audit under a User row lock. It creates no identity or authentication state. This command does not admit promotion through the full-v3 fixture guard; coordinator transition/disposal and operational acceptance remain open under [runbook 86](../../docs/prd/ops/86-admin-bootstrap-runbook.md).
