# Video storage and manifest checkpoint

`VideoManifestGateway` accepts an exact generation inventory of `{path, purpose}` entries. Paths are safe relative asset paths, not storage keys or URLs. Playback cannot read poster assets and poster authority cannot read stream assets. Playlist lines and quoted `URI` attributes are rewritten into the same grant namespace; unknown paths, traversal, external URLs, query/fragment escapes, malformed attributes and encryption are refused. The HTTP owner must authorize actor, current grant, Listing and generation on every request before using this module. This module does not serve bytes or establish HTTPS/cache/log redaction acceptance.

`S3VideoObjectStorage` accepts durable server session IDs and a configured explicit private bucket. It derives source keys, initializes multipart provenance metadata, reconciles paginated confirmed parts, signs exact expected part lengths, and completes using storage-owned ETags only. Prepared bytes are capped at the provisional 15 MiB limit, parts at 5 MiB and credentials at 15 minutes or the session deadline. S3 calls use abort deadlines. An abort acknowledgement is not cleanup completion; durable cancellation and object/parts absence reconciliation remain required.

The caller must resolve `VideoStorageSession` from authorized persistence. It must recheck owner/account/target/tester authority and enforce cancellation/completion fences before and after storage operations. The adapter deliberately does not accept a client key or bucket, and is not yet registered in production DI. Private bucket policy, actual storage integration, concurrent cancel/complete reconciliation, generation adoption, processing/readback, bounded streaming HTTP and final native acceptance remain open.

Focused verification: eight manifest/storage behavior tests pass; API TypeScript and changed-file ESLint pass. Multipart red checkpoint `8e50f5ea` failed three assertions with `NOT_IMPLEMENTED` before implementation. The earlier manifest run failed at module import and is not valid behavioral red evidence; current green tests provide positive coverage only.

Docs: https://docs.aws.amazon.com/AmazonS3/latest/userguide/abort-mpu.html confirms abort is separate from verification of in-flight parts. Installed SDK command declarations were inspected for multipart request/response shapes. No dependency or version change.

Multipart uncertainty support now adds exact-key initialization discovery and source HEAD reconciliation. An already durable initialization intent may recover its storage UploadId from bounded paginated listing of only its unique source key. Multiple exact matches or pagination uncertainty fail closed. An empty result is still uncertain and must never trigger another CreateMultipartUpload for the same key. Completed-source reconciliation requires both exact expected length and server-created session/upload metadata; it does not prove hash/codec validity. Seven focused storage tests pass locally. Concrete durable protocol orchestration and hosted provider races remain required before registration.

`OwnedVideoUploadProtocol` now orchestrates durable-reservation and storage ports without crossing database transactions with I/O. Initialization is attempted only for the reservation's one create intent; replays use exact-key discovery. Completion checks owned source provenance, reconciles a lost response and commits only under the same durable fence. It also gets confirmed parts, renews bounded requested credentials with a post-I/O authority check, and delegates persisted pause/resume/cancel. Five boundary tests cover idempotent create, lost create/complete responses, pause/renewal and cancellation winning completion. The concrete new ledger and V1 HTTP route are not registered yet; the historical partial route still requires replacement. These tests do not establish real database races or complete #890.

The partial upload route is replaced by additive `/api/v1/listing-video-upload-sessions`. Strict contracts accept only protocol version, draft/listing target, prepared size/hash, poster offset and idempotency key. Every controller method requires a verified JWT session and tester upload eligibility; bodies never carry actor, source key or upload id. Status, credentials, pause, resume, complete and cancel responses use `private, no-store`, and capability errors are generic. The Prisma ledger creates a target-fenced generation and video-v1 MediaUpload in one transaction, stores idempotency hash/completion fence, uses row locks for actor/target/upload/session, and writes processing/cleanup work without holding locks across storage. It does not yet have hosted PostgreSQL race evidence, worker queue registration, native transfer/player acceptance or final cleanup worker; rollout remains closed.

Two HTTP and five protocol boundary tests pass after this checkpoint. API TypeScript and changed lint pass. The pre-existing legacy repository remains as a compatibility provider and must be removed or isolated before final acceptance if no other caller uses it. The current module composes both old repository and new V1 ledger; the new controller consumes only the V1 protocol.
