## Material findings

### 1. Execution exclusion is still an unimplemented prerequisite

`scripts/staging-quiescence.mjs:32-52` requires one running candidate instance per API/worker service. Lines 155-204 perform maintenance, history, log and remote observations and then always throw `QUIESCENCE_EVIDENCE_GAP`. This is correctly closed. `staging-clean-reset.mjs:154-181` would accept caller-shaped observation fields, candidate issuer SHA and two timestamps separated by the constant 900. Those helpers cannot become the authority by wiring the observer's fields into them. `staging-clean-reset-remote.mjs:63-74` similarly validates a Redis binding's shape and 900-second arithmetic; lines 370-375 explicitly say that binding is synthetic controller context, not live closure proof.

The current proposal's step 2 is directionally right, but it must specify the provider invariant and automatic restart cases rather than require an undefined perpetual hold. Desired replicas must be zero in every configured region, actual application instances must be terminated, and pending rollout/cron/wake mechanisms must not be able to produce execution under that desired state. Read all current relevant deployments, not just latest or one active deployment. A successful stop reply, `SUCCESS` deployment status, absent heartbeat, elapsed interval or second matching snapshot does not establish that invariant.

The existing controller has no `cleanReset` method. `staging-control.mjs:115-121` already retains an open operation and excludes ordinary commands; `:166-250` provides durable operation intent and blocked recovery. Extend that contract, rather than add another lease store. `staging-ledger.mjs:80-92` provides explicit-revision Git CAS and treats a failed push as ambiguous. CAS serializes cooperating operators; it is not a process fence and does not revoke an executor already admitted before CAS changes.

### 2. Scale-zero conflicts with the present remote execution transport

`staging-railway.mjs:106-113` executes remote work via SSH inside the API service. `staging-clean-reset-remote.mjs:80-87` requires that process to have the exact API service identity, candidate and internal database origin. Stopping every API instance removes that execution host. The MinIO image is minimal and its owning contract specifies no shell health probe, so do not presume it supplies Node, psql or an operator shell.

Resolve this before claiming an executable protocol. The smallest existing-code option is a specifically admitted **maintenance-only API execution host**, with the worker and every business process stopped. `apps/api/src/main.ts:19-25` branches before Nest creation; `apps/worker/src/main.ts:10-13` branches before application-context creation. Automatic restart of that exact verified maintenance deployment may be safe, whereas restart of an old normal deployment is not. Prove deployment environment-snapshot semantics, exact entrypoint and absence of business child processes. Maintenance flag/readiness alone is insufficient, and launching such a host is a journaled transition, not permission to restart an arbitrary old deployment.

If that maintenance host cannot be proved without changing protected runtime configuration, use an already available authenticated operator connection to the exact data services and adapt only the transport/target binding. Reuse the fixed row/Redis programs and recovery semantics. This review does not assert that such an independent connection exists. The concrete prerequisite is a verified non-business execution path to PostgreSQL, Redis and S3 while application execution remains excluded. Do not silently relax the API identity checks, add public database exposure, or create an unreviewed helper service.

### 3. The exact MinIO build does not provide a universal seven-day outstanding-grant bound

Essential official source reads succeeded for commit `df34868a88cc8c396807e04a7e220810b321bdaa`, the version attributed by the proposal to `RELEASE.2026-09-22T19-25-18Z`:

- [signature-v4-parser.go, lines 220-233](https://github.com/minio/minio/blob/df34868a88cc8c396807e04a7e220810b321bdaa/cmd/signature-v4-parser.go#L220): `X-Amz-Expires` must be nonnegative and no greater than 604800 seconds.
- [signature-v4.go, lines 260-267](https://github.com/minio/minio/blob/df34868a88cc8c396807e04a7e220810b321bdaa/cmd/signature-v4.go#L260): a signed date more than `globalMaxSkewTime` ahead is rejected at admission; expiry compares `UTCNow() - signedDate` against the requested duration. [globals.go:96-98](https://github.com/minio/minio/blob/df34868a88cc8c396807e04a7e220810b321bdaa/cmd/globals.go#L96) sets skew tolerance to 15 minutes.
- [signature-v2.go, lines 164-180](https://github.com/minio/minio/blob/df34868a88cc8c396807e04a7e220810b321bdaa/cmd/signature-v2.go#L164): the presign path parses an absolute `Expires`, rejects an already-expired value and checks the signature. It supplies no seven-day duration cap.
- [auth-handler.go, lines 133-150, 364-374 and 597-606](https://github.com/minio/minio/blob/df34868a88cc8c396807e04a7e220810b321bdaa/cmd/auth-handler.go#L133) recognizes/supports SigV2, SigV4, POST-policy and other authentication families. Reading the V4 parser alone is not a proof about every accepted write authorization.

This does not show that Carberk actually issued V2 or future-dated URLs. It shows why a storage-wide cap cannot be inferred from this build. A previously signed future-dated V4 URL may be rejected now and become usable later. The 15-minute request-admission skew does not retrospectively bound the date that a signer put into an undisclosed URL. Need either an already effective server admission restriction covering all actual grant families, or actual issuance authority proving protocols, maximum expiration and signer-clock bounds. Do not turn that into a demand for complete historical request logs. A verified issuance implementation/configuration chain covering the outstanding interval, with a defensible clock bound, can suffice. A new ledger cannot recover earlier unrecorded grants.

`staging-clean-reset.mjs:17-25,122-139` pins current source definitions and reports 900 seconds. That is a source-change guard only. It scans selected import/call text, not every possible signer implementation or historical deployed artifact. `PresignUpload.ts:71-97` signs before recording its upload row; personal-chat and logo presigns also supply no complete durable grant ledger. A database-row count is not issuance completeness.

### 4. Expiry and SDK cancellation are not accepted-request drain

`S3VideoObjectStorage.ts:35-38,55-74` directly creates/completes/aborts multipart sessions and signs part URLs. Its own comment says abort acknowledgment is not deletion evidence. `S3DiagnosticObjects.ts:41-49`, `MinioServicePrivateStore.ts:16-22` and worker `S3VideoProcessingObjects.ts:41-48` make direct writes with caller abort deadlines and lost-reply handling. Killing the client or expiring its URL does not prove that an already authenticated storage request cannot finish.

A same-service MinIO stop/restart is the smallest proposed drain boundary. It is sufficient only when all old server processes and their accepted sockets are actually gone, with no second replica, old deployment, alternate listener or persisted replay actor left. A reverse proxy may retain a client connection or buffered body across backend death. After the authoritative expiry horizon, a retry to the new server must fail authentication, or its completed effect must already be included before inventory. Verify this on public and private paths. Do not equate `deploymentRestart: true`, graceful shutdown initiation, health recovery, PID reuse or `drainingSeconds` with process/socket death.
