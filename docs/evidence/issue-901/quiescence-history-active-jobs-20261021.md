## Source changes

`Query.deployments(input: DeploymentListInput!, first: Int, after: String)` is read separately for the exact project, environment and API/worker service IDs, with `includeDeleted: true` and no status filter. Every returned page is consumed until `hasNextPage` is false. Missing/invalid page metadata, mismatched or repeated cursors, duplicate deployment or instance IDs, missing current deployments, cross-target nodes, missing/invalid commit hashes and unknown deployment/instance states refuse. The 1,000-page resource bound refuses instead of returning a truncated inventory. Both histories are freshly reread after the runtime observations and any difference refuses.

Each history record binds its deployment ID and possible prior issuer to `meta.commitHash`, project/environment/service, `createdAt`, `updatedAt`, nullable `statusUpdatedAt`, `deploymentStopped`, status and instance IDs/statuses. An older deployment of the current candidate SHA is still treated as a possible prior issuer. A prior deployment with a pending/sleeping/removing/success state, missing stop flag, or potentially running/restarting instance refuses. Even the conservative stopped-state combination is only an observation. It does not claim irreversible termination or inability to restart.

The fixed remote program now reads `LLEN` on each of the 12 BullMQ queues' `toKey('active')` lists. Positive, malformed, unavailable and unsupported results refuse before API/database observation. Only a raw safe integer zero is accepted as a bounded read. `skipMetasUpdate: true`, the BullMQ version pin, existing worker/heartbeat checks and connection timeouts remain. No Worker is constructed, no queue action is invoked and no queue metadata/job is changed. The challenge-bound receipt requires exactly all 12 active-job counts; missing/extra/nonzero counts refuse.
