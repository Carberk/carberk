## Recommended ownership boundary

Service messaging owns the synthetic case/request and conversation graph. Identity continues to own current Session, elevation, grant and deletion authority. Extend the reservation journal by exact keys and validated edges, never by actor alone, VIN, provider, date, object prefix or synthetic mode alone. The [schema](../../../packages/db/prisma/schema.prisma) defines actual keys and nullable linkage.

## Shared capacity/provider decision

Current ordinary setup is an assigned, elevated `history.fulfilment` operator calling `POST conversations/:id/history` with `kind: capacity`, expected assignment version, today/tomorrow Ashgabat day, slot/morning limits, evidence and provider allowance/consumed/resetAt/evidence. [History operations](../../../apps/api/src/modules/service-messaging/infrastructure/history/PrismaHistoryOperations.ts) validates these inputs, but upserts global `history_capacity_days[day]` and `history_provider_allowances[provider,day]`. It neither proves absent keys nor restricts an update to its request. Synthetic mode defaults do not establish ownership.

There is therefore no source-backed safe reservation setup path today. Using an unused-looking day is insufficient: `accept` expires other held orders on that day and counts global reservations; `purchase` selects global paid FIFO and increments shared allowances. Existing e2e capacity HTTP calls and direct DB setup are contracts, not an authorized operator setup recipe.

Recommend a reservation-scoped synthetic capacity/allowance partition, including order capacity edges, acceptance expiry/counts, provider reservation counts, purchase FIFO and worker selectors/locks. Bind the partition to the verified current candidate/reservation server-side, never a client-selected ownership claim. Keep ordinary quote/payment/artifact HTTP and current authorization/policy gates. Service messaging owns this source change; #901 owns journal/reset integration and refusal tests. No bootstrap insertion of capacity or allowances is recommended.

After that change, the existing capacity command is the setup interface for `history-fulfiller`, admitted and assigned normally, using explicitly synthetic inputs. Its keys must be newly created in the reservation partition or already journal-owned there. Keep global rows outside ownership. Never adopt, delete, decrement, restore or snapshot-and-replay shared unknown state. Until this partition and its tests exist, reject capacity/purchase/accept paths that would touch global state and keep full History admission closed. A founder's real morning/provider input remains a separate activation prerequisite.

## Retention, queues and exact disposal

[Campaign journal/reset](../../../scripts/staging-campaign.mjs) currently tracks auth/business families, not these service/History families or their private objects/general workers. Recommend retaining redacted `service_audits` alongside existing redacted `audit_logs`: keep exact audit ID, purpose/action and assignment version; clear actor/target staff, reason and resource linkage after recording a redacted reservation receipt. Integrity and terminal checks must explicitly recognize these retained rows. Do not erase service audits merely to make reset pass. This is proposed policy requiring approval, not current reset behavior.

At account deletion, preserve the existing distinctions in [serviceAccountErasure](../../../apps/worker/src/jobs/serviceAccountErasure.ts): detach private linkage, honor specific holds and payment schedules, and permit licensed anonymous vehicle knowledge independently of Support's 90-day schedule. At final synthetic reservation reset, recommend disposal of all owned synthetic content and private bytes, including reusable anonymous artifacts, after joined reuse assertions. An active hold or unclassified rights/disposal blocks reset; it does not authorize bypass. Retain only approved redacted audits, journal receipts and existing delivery tombstones.

Preserve runtime SHA, migration/schema/trigger/journal/delivery hashes, reservation and fixed15 binding at fixture, mutation and reset. Keep the current `identities → cleaning → disposed` barrier and fail-closed retry. Workers and uploads must join that barrier before writes/storage effects; existing lifecycle epochs alone do not bind a reservation. Serialize with current principal/Session, owner/conversation and sorted day/provider locks; preserve FIFO ordering and 5s/20s limits. Pause an in-flight upload/push/expiry/advance before reset and resume afterward to prove no rows, bytes, sends or audits resurrect. Account restoration must not revive content. A storage failure leaves cleanup pending and the reservation blocked, never a successful reset receipt.

## Final bounded disposition

Support text-only RED is the next family after the contact writer vacates `CampaignFullV3.e2e.spec.ts`. This disposition authorizes no concurrent edit and no source/schema/test implementation.

Feasibility in the [actual schema](../../../packages/db/prisma/schema.prisma): `ServiceAudit.actorId`, `reason` and `targetStaffId` are nullable; only `actorId` has a User FK, with `SetNull`. `resourceId` is a non-null scalar without an FK. Retention must clear nullable identity/text fields and replace `resourceId` with a non-identifying terminal marker, or explicitly design a schema change; it cannot set that field to null. Keep the exact audit ID linked from its retained `campaign_records` key and redacted terminal receipt, so reset integrity proves the retained row's disposition without retaining customer/resource linkage. Existing reset predicates/redaction must be extended for `service_audits`.

`HistoryArtifact.acquiredForOrderId`, `sourceListingId`, `verifiedById`, VIN/provenance/facts linkage are nullable scalars, while `objectKey`/`sha256` remain non-null. `HistoryDelivery.orderId`, `artifactId`, `purchaseIntentId` are non-null Restrict FKs. Exact terminal deletion therefore requires owned deliveries removed before artifacts/intents/orders, owned booking/payment/refund children before orders, and owned orders before quotes/requests/capacity; scalar archive references and cleanup keys still need explicit validation/disposal. Never invent nulling a non-null FK. Persist exact key/hash cleanup proof before deleting artifact metadata; block on foreign references or unresolved holds/schema constraints.

Minimal partition proposal, still unapproved: [schema models](../../../packages/db/prisma/schema.prisma) `HistoryCapacityDay` and `HistoryProviderAllowance` need a server-bound reservation scope in their day and provider/day keys, with `HistoryOrder.capacity` using the matching composite scope/day FK and order indexes supporting scoped day/state and paid FIFO. Default `mode='synthetic'` on capacity/allowance/request is reusable admission metadata but supplies no reservation isolation; today all synthetic reservations share those keys. No existing discriminator solves this.

[PrismaHistoryOperations](../../../apps/api/src/modules/service-messaging/infrastructure/history/PrismaHistoryOperations.ts) must propagate that scope through capacity upserts, day/provider locks/lookups, accept's expired-held update and active/provider-reserved counts, verify's day lock, and purchase's paid FIFO, allowance increments and FIFO lock. [PrismaServiceMessaging](../../../apps/api/src/modules/service-messaging/infrastructure/PrismaServiceMessaging.ts) archive/report selectors must constrain artifacts/orders to the same journal-owned graph. These are application/schema changes beyond fixture guards; ordinary auth/assignment/rights gates stay in place.

[AdvanceHistoryOrders](../../../apps/worker/src/jobs/AdvanceHistoryOrders.ts) needs scoped candidate/reread/day locks plus scoped artifact-retirement and payment-schedule SQL. [ExpireServiceContent](../../../apps/worker/src/jobs/ExpireServiceContent.ts) and [DeliverServicePush](../../../apps/worker/src/jobs/DeliverServicePush.ts) need reservation-aware selection and transactional barrier checks for cases/files/cleanup/outbox, retaining exact epochs/keys and unrelated work. Existing empty-data shared scheduled jobs remain shared. #901 must add journal keys, terminal audit linkage, collision/foreign-edge refusal and late-worker/reset proof for the eventual chosen design. No source decision or activation follows from this documentation.
