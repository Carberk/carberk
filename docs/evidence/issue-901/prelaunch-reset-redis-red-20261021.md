## Decision and proposed interface

This is an **implementation proposal, not canonical policy**. The [acceptance contract](prelaunch-clean-acceptance-contract-20261021.md) remains authoritative. Inspection of `cleanResetMain` found exact-key validation for only `inventoried` and `rows`, with database-only origins. The smallest extension is a Redis-only branch in that same serialized `cleanResetProgram` entrypoint, before PostgreSQL access. Existing database phase shapes remain unchanged. No future module, generated model, application bootstrap or caller closure claim is assumed.

Safe deletion replay needs a root disposition first. The [S2A receipt store](prelaunch-reset-s2a-db-source-20261021.md) has `operation_id` as its sole primary key and accepts only phase `rows`. Its PostgreSQL transaction cannot atomically commit Redis deletion. A second phase cannot simply reuse that row, and a Redis delete followed by a PostgreSQL receipt has a lost-response gap. Decide where the Redis phase's durable intent/completion lives, how it binds the existing rows receipt and survives interruption, and how retained receipts are eventually removed. An atomic Redis receipt has different durability/retention and control-namespace implications from PostgreSQL recovery. This checkpoint chooses neither. **Scope stops at read-only inventory and required refusals; no source GREEN or deletion-success claim.**

Strict proposed transport shapes:

- Observation payload has exactly `{ operation:'clean-reset', phase:'redis-inventoried', operationId, reservationId, candidate, identity }`. The IDs are strict 32-character lowercase hex strings; candidate is a strict 40-character lowercase SHA. `redis-inventoried` is a remote transport selector, not a new canonical S1 ledger phase.
- `identity` has exactly `{ projectId, environmentId, services:{api,worker}, origins:{database,redis} }`. Redis origin is credential-free, canonical `redis://redis.railway.internal:6379/0` in this fixture. Reject malformed, credential-bearing, extra, missing or cross-target claims before opening a client. Use the existing CLI's pinned project/environment/API/worker identities as trusted constants, plus the existing in-container environment and candidate checks. A caller's worker ID alone is no attestation. Do not invent a worker-ID environment variable.
- Observation receipt has exactly `{ operation, phase:'redis-inventoried', operationId, reservationId, candidate, identity, state:'observed', digest, queues, entries }`. `queues` lists the fixed 12 names in source order, each with exactly `{name,counts:{waiting,delayed,completed,failed,active,paused,prioritized,waitingChildren},repeatRecords}`. `repeatRecords` counts both legacy repeat registrations and modern scheduler registrations in the pinned BullMQ repeat index.
- Each entry is exactly `{keyDigest,type,count,contentDigest,expiresAt}`. Hash the key and Redis DUMP bytes with SHA-256; `count` is cardinality for collections and 1 for a string. `expiresAt` is Redis PEXPIRETIME, including -1 for persistent keys. Aggregate `digest` is SHA-256 of the JSON entry array sorted by keyDigest. No raw job data, result, error, destination, key containing identity data, Redis URL credentials or server diagnostics belong in receipts/errors. Job hashes, indexes, metadata and scheduler records all contribute, so equal counts cannot hide changed content. Observation must be coherent and bounded; an ambiguous concurrent read refuses rather than certifying a mixed snapshot.
- Reserved deletion payload has exactly the observation fields with `phase:'redis'` and `expectedInventory:{digest:<64 lowercase hex>}`. Malformed shapes refuse `Clean reset refused: target`. Every well-formed deletion/retry currently must refuse `Clean reset refused: Redis completion receipt authority unavailable`, with no writes. No caller-supplied key list, prefix list, quiescence flag or preservation list is accepted.

## Exact scope and next deletion obligations

The queue set comes from `scripts/staging-clean-reset.mjs`, `apps/worker/src/operations/watchdog.main.ts`, and worker composition: `video-transcode`, `notification-fanout`, `orphan-cleanup`, `account-purge`, `retired-upload-cleanup`, `listing-view-retention`, `measurement-retention`, `measurement-outbox`, `service-lifecycle`, `service-push`, `diagnostic-artifacts`, `email-code`.

Inspect every exact queue key, including meta, events, IDs, marker, indexes, job hashes, logs and scheduler/repeat records. An arbitrary key under a known queue prefix is not automatically approved. Unknown queues or unknown queue structures refuse `unknown Redis application state`. Active jobs or an `operations:<scope>:worker` heartbeat refuse `Redis producer or active job present`. An old `bull:email-code:de:campaign-cf_*` control tombstone without its verified retained SQL delivery ledger refuses `Redis control disposition unavailable`. Q1 retains only expressly verified control metadata, never disposable queue contents. This Redis-only checkpoint cannot validate that ledger and preserves nothing by assertion.

Additional actual source-owned data exercised here: `identity:reserved-phone-attempt:<sha256>` from `RedisReservedPhoneAttemptLedger`, `email:daily-sends:<UTC day>` from `RedisDailySendCap`, and `measurement:cap:v1:<window>:<subject>` from `RedisMeasurementRateLimiter`. The earlier reference inventory's generic session/cache wording does not establish additional executable prefixes. Monitoring configuration/state and foreign namespaces are outside deletion. A complete ownership classification, bounded inventory and source-backed structure recognition remain prerequisites for deletion; the three fixtures are not permission to delete other prefixes.

After the receipt decision, deletion must reverify the exact inventory immediately before an atomic compare/delete, refuse any new/missing/changed app state, delete only the exact observed in-scope keys and prove all 12 queues, schedulers and disposable app keys are zero. Foreign keys, Redis configuration, credentials and verified out-of-scope tombstones must survive. No FLUSHALL/FLUSHDB, broad prefix delete or Queue.obliterate. Lost response must recover only the same operation/reservation/target/candidate/expected inventory and exact recorded post-state. Different identity or producer drift must refuse without further effects. These deletion/replay assertions are deliberately deferred, not covered by a preservation-only substitute.
