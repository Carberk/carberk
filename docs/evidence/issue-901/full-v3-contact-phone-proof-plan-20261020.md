## Actual path and current barriers

- [IssueContactPhoneCode](../../../apps/api/src/modules/identity/application/IssueContactPhoneCode.ts) generates six digits, reserves a hashed `listing_contact_phone` database purpose with phone/channel/destination, seller, business and IP, commits, then sends synchronously. Codes expire after five minutes; destination/IP budgets and cooldown span purposes. A failed send leaves its reservation counted. Runtime contract purpose is `listing-contact-phone`. Production response has no `testCode`; CI-only `OTP_TEST_MODE` is excluded.
- [ConfirmContactPhoneCode](../../../apps/api/src/modules/identity/application/ConfirmContactPhoneCode.ts) uses `VerifySignInCode` and `PrismaOtpRequestRepository.findLatestForPurpose`, bound to purpose/channel/destination/user/business. It checks expiry and five attempts, then `consumeIfUnused` claims once. Wrong code increments attempts; another purpose does not. Confirmation never creates a Session or Sign-in Method.
- [HttpOtpSenderAdapter](../../../apps/api/src/modules/identity/infrastructure/HttpOtpSenderAdapter.ts) logs masked last-four phone, eight-character request tag and code in mock mode. Gateway mode builds rendered text but only logs without code. Neither sends SMS; neither uses the email campaign fence or protected sink. A successful log call proves neither a real delivery nor exact disposal.
- `ContactPhonesController` exposes `POST /api/v1/me/contact-phones/request` and `/verify`, HTTP 200, strict `{phone}` / `{phone,code}` bodies. Explicit `x-business-id` selects business context; token supplies current user/session. `RequestContactPhoneCode` and `ConfirmContactPhone` require current Owner authority. Sales may reuse the business's confirmed number but cannot request or confirm it.
- Business confirmation calls `PrismaBusinessContactPhoneRepository.record`, reauthorizes in its transaction, and updates only the admitted Dealership's `contactPhone`, `contactConfirmedAt` and automatic `updatedAt`. It creates **no** `verified_contact_phones` row and no business audit. Personal confirmation uses that separate table. `ContactPhonePolicy` gives business proof seven days and never substitutes the Owner's account phone.
- Consumption and Dealership update are separate transactions. Authority loss or reset between them can leave a consumed code without proof. Preserve that refusal; do not repair it by seeding verification or making a new atomicity claim.
- [staging-campaign.mjs](../../../scripts/staging-campaign.mjs) currently refuses phone/business/contact-purpose OTPs as `Unsupported campaign OTP`, before sender execution. Its ledger/sink are email-shaped, sign-in-only; `withCampaignEmailDelivery` requires an email alias and exact live request/hash. It cannot accept an SMS by relabeling a destination as email.
- At `794ac50a`, admission adoption works but subsequent admitted-business membership/redemption remains closed. Contact proof needs the separately verified admission/Owner prerequisite. Root Dealership stays synthetic `recovery` with null `contactConfirmedAt`; its deterministic `+999...` contact fails `PhoneTm` and is not reusable for this HTTP proof. Later redeemed/settings guards and admission audit/version integrity must explicitly permit the bounded contact update rather than open arbitrary Dealership mutation.
