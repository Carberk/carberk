## What D2 and D3 still require

### D2: cross-visit vehicle continuity

[ADR-0104](../../adr/0104-center-diagnostics-with-private-and-public-reports.md#L20) explicitly permits documented manual matching when VIN is unavailable/nonstandard and requires association revalidation after identity/ownership changes. A permanent VIN-only implementation would narrow this scope. [Feature 50](../../prd/features/50-reports-tier.md#L106) and [flow 66](../../prd/flows/66-diagnostic-inspection.md#L99) require linked new observations while preserving the original history and audience.

Current source establishes only per-order identity:

- [The observation contract](../../../packages/contracts/src/schemas/diagnostics.ts#L23) accepts `vin` or `manual`, requiring the corresponding nonempty VIN/reference. A manual reference is text, not a canonical vehicle identity or a cross-order attestation.
- [Observation persistence](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticIntake.ts#L204) compares a VIN observation with the current Listing VIN and records the current Listing digest for public orders. Manual observations also get that association, but no source rule compares two manual references or a manual observation with a VIN observation.
- [The digest](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticIntake.ts#L15) includes Listing id, seller, business, VIN, brand, model and year. [Association invalidation](../../../packages/db/prisma/migrations/20261015280000_diagnostic_association_invalidation/migration.sql#L1) clears validation on identity/ownership edits. Equal Listing ids do not establish historical vehicle continuity; equal old/new digests would also exclude legitimate ownership changes.
- Private intake can name a Listing without owning it, and can omit a Listing entirely. Its observation path does not validate a public association. Equal commissioner alone cannot establish that two private visits concern the same vehicle.

Settled positive: two VIN observations with equal trimmed uppercase VINs, same public Listing, fresh new-order consent and current validated association, as the joined case supplies. Never copy old observations, findings or identity validation into the new order.

Unresolved decision for root: what evidence and actor attest continuity for manual/manual, manual/VIN, corrected VIN, changed Listing identity, and private visits without a common Listing? Does a proven different vehicle refuse linkage outright, while an identity correction requires an explicit attestation? Define the durable input/proof and failure behavior. Equal free-form references, same Listing, new consent, and equal commissioner must not silently substitute for that decision. The source slice cannot invent an identity registry, commissioner consent field, or a technician override for these cases.

### D3: public commissioner transfer

[ADR-0104](../../adr/0104-center-diagnostics-with-private-and-public-reports.md#L16), [feature 50](../../prd/features/50-reports-tier.md#L34), and [flow 66](../../prd/flows/66-diagnostic-inspection.md#L69) settle private behavior: another commissioner gets no private history through Listing ownership, dealership membership, payment or a known id. Require equal **non-null** commissioners for a private link, equal private audience, and independently established D2 continuity. Never allow private/public links in either direction.

Public readership is free and independently gated. [Public intake](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticIntake.ts#L64) authorizes the current seller/business actor and records that user as commissioner. [Public access](../../../apps/api/src/modules/diagnostics/infrastructure/DiagnosticReportAccess.ts#L22) requires that report's own consent, association and eligible Listing. Neither rule says whether a newly authorized publisher may create a cross-commissioner successor of an old public report. Revalidation is necessary, but does not define that linking policy. A different dealership employee can also mean a different commissioner without a vehicle ownership transfer.

Unresolved decision for root: may a fresh public commission link a public predecessor after commissioner or publisher changes, and what continuity/consent proof is required? Or must it start a separate public history? Do not impose same-commissioner equality on public reports as though approved; do not accept any current publisher merely because intake succeeds. Either choice must retain the predecessor's original audience and authorization, with no historical snapshot or commissioner rewrite.

## D5: safe lineage projection

Security is settled by the original-audience and specifically-authorized-staff rules. Display of an inaccessible report's identifier is not authority to read it. The existing implementation is insufficient for cross-order metadata disclosure:

- [`dto`](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticReports.ts#L46) finds any non-erased snapshot-backed successor and returns its id, with only a `staff` boolean and no subject. Staff assigned to predecessor A need not be assigned to successor B. The proposal's unchanged query would disclose B's id and existence to A-only staff.
- [The public reader](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticPublic.ts#L37) similarly tests only successor snapshot/non-erasure, not successor public eligibility, withdrawal or its order's erasure. A released snapshot alone is not a currently available public report.

Choose the minimum disclosure implementation: preserve existing same-order correction behavior; for a cross-order `supersededBy`, project the id only when the caller independently has current read authority for the successor, or the successor independently passes its public-reader gates. An A-only staff assignment supplies neither. An authorized private commissioner can still follow their released/withdrawn history. Anonymous readers see a cross-order link only while the linked report is publicly available. Do not expose draft successor ids through predecessor reads. Never grant a new assignment or expand predecessor readership as a side effect of linking.

The technician creating B necessarily knows the supplied predecessor id. Returning `successorOf` as the link acknowledgement does not return A's content or authorize A's read. Subsequent report, PDF and evidence requests continue to authorize against each requested report's own order. Any additional cross-order navigation must apply those same independent gates; no recursive lineage expansion.

This is a projection change, not a snapshot rewrite. Leave historical `snapshot`, hash, findings, template and PDF bytes untouched. Preserve the stored lineage even when a current response suppresses an unavailable successor id. Do not implement authorization by calling `load`/`loadPublic` recursively from `dto` after one order/report is already locked: that introduces another multi-order lock path. Use a narrowly scoped projection check with current authority/gates and a consistent lock plan. D5's optional broader staff visibility still needs an explicit decision if desired; it is unnecessary for the joined test. D4 labels/copy remain separate, since readers currently call all successors corrections.

## Evaluate the proposed mechanism

### Discriminator, index, INSERT and UPDATE

The proposed `reinspection BOOLEAN NOT NULL DEFAULT false` is a useful internal discriminator. Existing originals and same-order corrections remain false, so there is no historical classification backfill. Preserve the existing unique `predecessorId`, self-FK and snapshot guards. Make the discriminator part of immutable report identity. Do not infer it merely from a non-null predecessor, which also describes corrections.

The replacement partial unique index `UNIQUE ("orderId") WHERE "predecessorId" IS NULL OR reinspection` correctly makes a reinspection the new order's first report while allowing later corrections. Require `reinspection=true` to have a non-null predecessor on a different order, the same audience and a real released snapshot. Preserve the false branch's existing same-order predecessor rule. The ordinary `create` existence check must recognize either first-report kind; otherwise the application reports a raw uniqueness error. A reinspection after an original and an original after a reinspection must both fail with `DIAGNOSTIC_REPORT_EXISTS`.

Cross-order INSERT admission must also require non-erased predecessor/report orders, private non-null commissioner equality, D2 proof, and the finally selected D3 public policy plus new-order public consent/association. Do not finalize that SQL with an unapproved VIN-only/public-commissioner rule. Existing order/template/audience pinning stays in force.

Evaluate mutable cross-order identity/commissioner/listing conditions **at INSERT**, never again on ordinary UPDATE. [Erasure](../../../apps/worker/src/jobs/diagnosticAccountErasure.ts#L7) locks orders then reports, fences reports/artifacts/evidence, and only then clears order commissioner, observation, consent, Listing and association. Rechecking predecessor relationships on UPDATE can block a surviving successor after predecessor erasure. Retain immutable identity and the exact old snapshot guard on UPDATE, including the existing own-live-order requirement and finalized/withdrawn state restrictions. Erasure intentionally writes reports before erasing their own order. No exception may make snapshot bytes, findings, observation, mileage, hash or finalization time mutable.

### Evidence boundary

The [current evidence walk](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticReports.ts#L95) rejects every cross-order predecessor, even for empty findings. Implement the stop by walking from the current report: include it; if it is a reinspection, stop before fetching its predecessor. Otherwise follow same-order, same-audience, non-erased correction ancestors with the existing cycle checks. A correction of a reinspection includes that reinspection's evidence and any intervening corrections, then stops. It must never fetch an erased earlier visit just to validate a surviving report.

Keep [private evidence reads](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticEvidence.ts#L72) and public evidence reads bound to the requested report's order and referenced finding. Do not permit cross-order inherited evidence. A prior-visit evidence id must produce `REPORT_EVIDENCE_UNAVAILABLE`, leaving draft version and findings unchanged, as the joined test requires.

### Retry and conflicts

Authorize the new-order technician before state/conflict responses. The joined authority negatives run after creation and must still return 403. A matching retry compares report kind, target order, predecessor, normalized reason, author and non-erasure, returns the current existing record without another report/audit, and does not fail merely because the order version changed after the first request. A different tuple or another consumed predecessor gives a conflict; stale version applies to a genuinely new creation. Never return an unrelated row found only by report id. Verify the immutable tuple on retry before bypassing initial preconditions.

Preserve ordinary correction behavior, with one necessary discriminator check. [`correct`'s existing retry branch](../../../apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticReports.ts#L155) compares successor id/reason/author but not its order/kind. After cross-order links exist, that branch could return B as a correction of A without B authority. Require the existing successor to be a same-order, non-reinspection correction before that retry returns. An existing reinspection must produce `DIAGNOSTIC_CORRECTION_CONFLICT`, even if id/reason/author match. This preserves correction semantics rather than treating a physical visit as an editorial revision.

Both paths retain predecessor uniqueness. Map only the relevant report-id/predecessor/first-report uniqueness races to documented conflicts, not arbitrary database exceptions. The controller already maps `CONFLICT`, `EXISTS` and `STALE` errors to 409. The new audit belongs only to B and records the link/reason once; do not mutate A or write an audit on an order the technician is not assigned to. D1 does not authorize fetching predecessor findings for display.

### Locks

The proposal's Listing -> sorted orders -> predecessor order is only the feature portion of the lock hierarchy. [`DiagnosticAuthority.order`](../../../apps/api/src/modules/diagnostics/infrastructure/DiagnosticAuthority.ts#L25) first resolves current identity, locks a public Listing before its order, then checks assignments/qualifications. [Identity](../../../apps/api/src/modules/identity/infrastructure/PrismaBusinessAuthority.ts#L8) locks the actor User and possible Business; [staff authorization](../../../apps/api/src/modules/identity/infrastructure/PrismaStaffAuthority.ts#L11) also locks the Session. Keep these existing fences.

Use unlocked minimal discovery only to identify candidate Listing/order ids, then acquire current actor identity fences, relevant Listings in stable id order, both orders in ascending id order, current B assignment/qualification fences, and predecessor report lock. Re-read and verify every discovered relationship after locks, including erasure, Listing id, audience, version and successor consumption. Check ordinary B technician authority before returning predecessor-dependent results. Do not call `authority.order(B)` first and then claim sorting both orders later repaired the lock order; B would already be locked. Add a narrow multi-order locking/authority composition rather than broad new predecessor authority.

A concurrent `correct(A)` locks A's order before A's report. Erasure locks affected orders in order before reports. With reinspection also acquiring both orders before A's report, neither needs a lower-order lock after taking that report. Listing edits hold Listing before invalidating public associations, so keep Listing acquisition before orders. Projection checks must not reverse this order. New rows cannot be locked before insert; uniqueness arbitrates competing new ids. This is a source lock plan, not tested proof of concurrency safety.
