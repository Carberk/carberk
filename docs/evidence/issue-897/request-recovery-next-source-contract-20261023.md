## Why keep opaque preparation

A client UUID attached only at successful commit is enough to discover completed records while retained. It leaves no same-Session server identity to discover when both the command and ID are lost before commit. More seriously, a replaying execute that creates on a missing client UUID cannot distinguish a rolled-back first attempt from a previously committed proof whose lawful disposal removed that UUID. It could issue a second logical proof after disposal. Avoiding that would require retained tombstones or a separate non-reusable issuance mechanism.

Opaque server preparation is the small selected mechanism. It stores no protected command, makes lost preparation discoverable, and makes execute require a still-existing identity. Proof disposal deletes the identity and missing identity can never execute. No pending selector beyond B/kind is necessary. Requiring recovery of unexecuted text would add scope with no criterion to justify it, so it is omitted.

## Smallest request lifecycle

Use two kinds, `issue` and `consume`, behind the existing diagnostic port. These signatures are proposed behavior, not shipped routes.

1. `prepare(B, kind)` allocates a server UUID and stores only request ID, authenticated actor ID, authenticated Session ID, B ID and kind. No A selector, selected technician, proof payload, command hash, reason, rationale, evidence, rights declaration or duplicate proof bindings. Authorize the current B reviewer or B technician capability respectively. Preparation grants no issuance/consumption admission and emits no business audit.
2. `execute(B, requestId, command)` requires an existing same-actor/same-Session/B/kind identity. For issue, command is the existing strict issuance object. For consume, it is the selected proof handle plus existing strict report ID/version/reason. First execution runs all existing admission and writes the request association onto the existing proof or B report in the same transaction as proof/report creation and existing audits. No command is persisted before that commit. Keep caller-provided report IDs.
3. `recover(B, requestId)` and bounded B-scoped request discovery return only opaque identity, kind and current authorized outcome. No command is required for recovery of a committed outcome. If there is no committed outcome under the request lock, return `pending_input`, meaning no command was committed. A pending identity is never a usable proof or stored command. The UI may request fresh input and explicit execute on that same identity after recovery/revalidation; it cannot execute it by ID alone.

The binding is actor + current Session + B + kind + request ID. Actor/Session come from authentication, never caller fields. Allocate request IDs only in prepare. Execute never inserts, upserts or revives a missing identity. Persist one unique request ID on its completed proof or B report. The existing record is the sole owner of committed command semantics; request metadata has no text copy and needs no command digest. Under locks, completion can be derived from that unique association rather than a second result payload.

A repeated prepare is a separate explicit pending identity. It cannot issue anything. A lost prepare response is recovered through same-Session bounded discovery with no retained browser ID. Do not automatically prepare again after an uncertain response. Multiple pending identities are opaque choices for explicit user action, not automatically selected attempts. Use the existing opaque continuation approach bound to actor, Session, B and query kind, with stable bounded traversal and no counts/global-absence claims from one empty page.

A new intentional logical issuance requires a new explicit prepared identity. Equal payload on different request IDs may issue distinct proofs and audits. Equal payload on the same request ID may not. Preserve legacy strict issuance behavior and the genuine 61 ordinary-proof traversal fixture. Add a separate strict recovery envelope/route or explicitly versioned contract; do not quietly reinterpret old POSTs or allow arbitrary new fields in old schemas.

### Exact replay and loss boundaries

| Situation | Required behavior |
|---|---|
| Prepare never commits, or its response is lost | No proof/report/audit exists from prepare. Reload discovers any committed opaque identity. Absence in a partial page or a transport error is not proof that prepare failed. Resolve uncertainty before another explicit prepare. |
| First execute is in flight and reload starts | Recovery acquires the same B/request serialization locks and observes the settled commit or rollback. An unlocked absence check cannot authorize a new attempt. |
| First execute rolls back or never reaches the server | The prepared identity remains `pending_input`; no command text was persisted. Explicit retry may supply fresh input under the same identity and full current admission. There is no committed payload to compare against or reconstruct. Never claim exact-command recovery for this case. |
| First execute commits but reply is lost | Same-Session discovery/recover returns the original proof handle or existing B result pointer associated with the request. No second proof/report/business audit. No command or browser cache is needed. |
| Explicit repeat execute after commit | Compare every validated command field with its existing committed binding after current authorization. Exact match returns the same minimal result. Changed payload conflicts. Recovery by ID is a read, so it needs no command comparison. |
| Two execute calls, same request | Serialize and re-read. Winner commits; exact loser returns the same result, changed loser conflicts. Audit failure rolls back association and all business writes. |
| Distinct requests, equal issuance payload | Each may issue its own proof and issuance audit under unchanged current policy. Never dedupe by A/B pair, payload hash, technician or time window. |
| Distinct consumption requests compete | Existing proof/report/A-successor/B-first-report uniqueness admits one result. The losing request cannot adopt the winning request/result as its own completion. An exact command without the winning request ID is not the winning request retry. |
| Invalidated, expired or erased unused proof | Refuse consumption. Restoring source values never revives it. Completed issuance recovery cannot issue a replacement or label the original usable. |
| Proof/request disposed | Execute on the missing request always refuses. It never allocates a new request. No personal hash or tombstone survives merely for dedupe. New issuance requires a separately explicit prepare and full admission. |

Issuance exact replay compares the strict validated input with the original proof: predecessor ID/version/identity pin, B version/identity pin, selected technician, method, rationale and provenance IDs. Reconstruct these comparisons from existing `content` and `bindings`; do not re-evaluate current A versions as the original command. Use a defined canonical treatment of existing validated fields, including trimmed text and provenance array semantics, consistently in first execution and replay. Do not persist another copy/hash of the command. Request binding additionally verifies issuer actor/Session and B. Only after current dual authority may a retained historical proof produce its original handle with explicit unusable status. Unreadable/disposed proof gives uniform unavailable, never reissuance.

Consumption exact replay checks request actor/Session/B/kind and the existing report/proof/version/reason binding through the established retry rules. The original reason remains only in B's existing report/audit storage; the rationale remains only in the existing proof. No pending copy or request-body logging. A retained request cannot turn an unrelated pre-existing report into its completed result.

## Consumed B survives A disposal

Do not call `admit`, revalidate the issuer, acquire A locks or return `dto(..., exactReceipt=true)`. Current ordinary JSON/PDF delivery keeps its existing erasure-safe projection. Ordinary authorized B writes/release remain independent of A admission.

New sign-in cannot adopt the prior request. Existing author-scoped B result discovery remains unchanged and may independently return its existing authorized pointer under a new current Session. Request identity access and ordinary B result access are different contracts.
