## Finding and dispatch boundary

A small server-owned request lifecycle can satisfy both recovery gaps without changing continuity admission. The current contracts cannot satisfy them unchanged. Implementation needs forward schema/contract changes and a classified pending-command lifecycle. The mechanical RED brief below is ready; a complete production writer must resolve the two specific decisions at the end before committing to pending-text collection or Session migration. This is not a request to reopen the approved B-only handoff, reviewer technician-name disclosure, dual-authorized pair reads, or supported same-visit manual/VIN recording corrections.

The safe minimum keeps opaque request identity and command material on the server. ## Proposed minimum request contract

Use one diagnostic request concept with two kinds, `issue` and `consume`. The following names describe the next implementation contract, not existing endpoints. Prefer a small extension of the existing port over a general idempotency framework.

1. `prepare(B, kind, command, classification)` creates an explicit new attempt and persists the validated immutable command under a server-allocated opaque request id, authenticated actor and Session. Actor and Session always come from authentication, never request fields. B and kind scope the binding. Issuance command retains all existing strict issuance fields; consumption command adds its chosen proof handle to the existing exact report/version/reason fields. Server allocation of report ids is optional only if it is persisted before returning preparation. Keep the current caller-provided report id in the minimal implementation. Before preparation persists any command, verify current issuer dual authority for issuance or current B technician authority and read-only `admit` for consumption, plus applicable classification/rights. Preparation emits no proof, report or business audit.
2. `execute(B, requestId)` accepts no replacement reason, report id, proof id or issuance payload. It executes the persisted command. Full existing admission runs inside this transaction before any first logical issuance or consumption. Preparation grants no future admission. Request completion, proof/report writes and existing business audits commit together.
3. `recover(B, requestId)` reads current status under current actor/Session authority. A bounded B-scoped discovery of that actor/Session's requests is also required because a reload can lose the prepare response and volatile id. Reuse opaque authenticated continuations scoped to actor, Session, B and query kind. No global count or false global-absence assertion. An unknown/denied handle must not reveal another actor's request. Discovery never executes anything or selects an unresolved operation automatically.
4. The returned state is `prepared`, `completed`, or a uniform `unavailable`. A recovered prepared command is not advertised as usable until current admission passes. If unusable, refuse execution. Do not return invalidation reasons or A facts to B. Client transport failures stay uncertain, not failed/absent. A database rollback leaves the same prepared request available for explicit execution after recovery. No durable `executing` lease is necessary when execution is one database transaction.

The exact binding is `(actorId, actorSessionId, B, kind, requestId)` plus immutable canonical command. Preparation allocates identity; exact retry means execute/recover of that identity. A prepared command cannot be amended. Execute accepts only the handle; replacement command fields fail strict validation. A repeated prepare is a new explicit attempt, never an automatic retry. If its reply is uncertain, discover existing preparations before offering another prepare. Duplicated preparations can create pending rows but cannot issue a proof or audit until explicitly executed by their distinct handles. A different authenticated actor, Session or B cannot adopt the request. Request ids are opaque selectors, not bearer credentials. Store the declared classification with restricted command content. Any command digest used for equality is restricted too; hashing neither anonymizes a reason nor establishes permission to retain it.

An intentional new attempt uses an explicit prepare action and receives a new server request id. It may issue a distinct proof even when every issuance field equals a prior request. Never dedupe by B, A/B pair, payload hash, technician, or time window. Maintain the existing legacy issuance behavior and strict schemas for old callers; add a separate recovery envelope or explicitly versioned request route. Do not silently reinterpret old POSTs as exact retries or loosen strict schemas to accept arbitrary fields.

For concurrent preparations, enforce uniqueness on the server request id and its exact identity above. Do not impose one lifetime request per B. Bound discovery and collection; exact execute/recover creates no extra rows. Do not add a new per-B draft/request limit without product authority. If multiple prepared attempts exist, show only bounded opaque choices/status through the eventual approved UI. Creating a new request never resolves an uncertain earlier one by itself.

### Lost replies and concurrency

| Failure or race | Required result |
|---|---|
| Prepare never reached the server or rolled back | Authorized discovery has no committed request. No proof, report or business audit exists. An explicit new prepare is allowed only after resolving the uncertainty; do not infer absence from one bounded empty page or transport error. |
| Prepare committed but its response was lost | Reload discovers that same server request and its exact command binding. Recovery exposes no protected command text to B. The recovered handle executes the persisted command; a new prepare must not be used to retry the uncertain one. |
| Execute response lost before transaction commit | Recovery serializes on B/request and observes the committed outcome after the transaction ends, or the still-prepared request after rollback. It must not report an unlocked snapshot as conclusive absence. |
| Execute committed but response lost | Recovery returns the original proof handle to a currently authorized issuer, or the currently authorized existing B result pointer to its technician. Explicit repeat execute returns that same outcome. No second logical issuance or business audit. |
| Two executes of one request | After normal feature locks, lock/re-read the request row. One transition wins. The other returns its authorized completed result. Audit failure rolls back the request completion and every proof/report/consumption write. |
| Distinct issuance requests with identical payload | Both may succeed under existing policy and each has its own proof and issuance audit. Preserve the genuine 61-proof traversal fixture. |
| Two consumption requests for one proof or competing B first reports/A successors | Existing proof/report/successor uniqueness admits one logical result. Exact winning request retries return that result. Losing distinct requests conflict or are uniformly unavailable as current authorization permits, never alias the winner. |
| Invalidated unused proof or restored source values | A prepared consumption request cannot revive the proof. Refuse. Intentional new issuance requires a new request and full current admission. Repeating an issuance request whose original proof is invalidated cannot mint a replacement. |
| Authority lost after prepare or commit | Current Session, user, grant, assignment and qualification fence every read/action. No disclosure of stored result, command, denial detail or existence to the now-denied caller. Restoring authority cannot clear proof invalidation. |

Issuance recovery is not proof reissuance. With current dual authority and retained lawful material, an issuer may recover the original handle as historical with explicit unusable status. If that disclosure is no longer authorized, return uniform unavailable. Never infer usability from a completed request. Do not reconstruct a disposed proof or retain a personal tombstone to distinguish disposed from never-issued requests. A disposed unavailable request is terminal for that handle; it is never recycled into a new issuance. Only prepare can allocate a new server id. Execute/recover on a missing id always refuses and never upserts. This avoids keeping personal dedupe tombstones after lawful disposal.

### Consumed B and minimization

Keep two separate lifecycles. Pending command material follows its declared restricted rights and current admission. Committed consumption identity attaches to B's existing minimal retry binding and surviving report lifecycle. It must not depend on retention of the proof or the pending request payload.

Persist the consuming actor/Session/request identity and immutable B/report/proof/version binding atomically with B creation. The existing report already stores the exact reason as `state.correctionReason`. Avoid a second long-lived reason copy in a completed request. Exact new execute retries load the stored command or committed B receipt server-side and return only `{requestId, state: "completed", result: {proofId, reportId}}`. They do not require the browser to supply the reason again. The new binding must remain immutable during ordinary B writes and obey B/staff erasure. No A identity, predecessor id or issuer Session is needed in this B receipt.

After A rights expiry/erasure or proof deletion, authorize B and the bound technician's current Session/grants/assignment/qualification, then read B's receipt/result. Do not call `admit`, compare A, revalidate the issuer, or acquire new A locks. The existing original command binding may remain server-side only where lawful. If B's reason has been erased, do not restore it from request storage. A current safe result pointer may survive without the reason; execute must never reconsume or invent the deleted exact command. Ordinary current B reads continue through existing erasure-safe projections. Preserve current JSON/PDF suppression of A lineage/reason and independent publication gates.
