## Findings, highest severity first

### P1. New order-writing source triggers can introduce a concrete deadlock

The handoff requires sorted diagnostic locks but does not reconcile the surrounding mutation transactions. Public diagnostics takes User → Business → Listing → order (`DiagnosticPublicBindings.ts:27`, `PrismaPublisherBindings.ts:12`). Account deletion first updates User, then locks Business/removes membership, then archives Listings (`apps/api/src/modules/identity/infrastructure/PrismaAccountDeletionUnitOfWork.ts:20`, `:53`). Adding an immediate User-change trigger that writes orders creates order → Business/Listing acquisition later in that same transaction.

Literal cycle: deletion T1 holds User U and its new trigger locks visit O, then T1 waits for Listing L during archival. A concurrent personal Listing identity edit T2 holds L and its association trigger waits for O. Personal Listing save does not take the diagnostic User prefix (`apps/api/src/modules/listings/infrastructure/PrismaListingRepository.ts:108`, `:119`; `20261015280000_diagnostic_association_invalidation/migration.sql:6`). Sorting only O rows cannot break L → O → L. This is a proposed-change risk established by source ordering, not an observed runtime deadlock.

Required correction: discovery and the complete sorted User/Business/Listing lock prefix must precede the first trigger-induced order write in each affected writer. Include account scheduling/purge, membership redemption/recovery/removal and business status changes. Do not repair a trigger by acquiring historical Users after it already holds Business or order. Recovery currently locks the founder/new owner before Business and only then discovers/deletes the previous owner's membership (`apps/api/src/modules/identity/infrastructure/PrismaBusinessRepository.ts:125`). OLD member user/business and historical fact targets must be discovered before the relevant prefix, with target revalidation/refusal when discovery changes. Define any needed writer changes explicitly; a SQL trigger cannot reorder locks already acquired by its caller. Keep order/report/assignment/proof sequencing after that prefix. Lock the whole affected order set in sorted order before multi-row updates, rather than relying on UPDATE scan order or independently sorted row triggers.

### P1. Eligibility transitions are broader than approved permanent ownership refusal

Handoff line 28 includes all bound participant/business eligibility changes and membership roles in the irreversible witness. ADR-0108 distinguishes unchanged identity/ownership from current publisher authority and permanent invalidation of an already issued proof (`docs/adr/0108-pair-bound-diagnostic-reinspection-continuity-proof.md:22`, `:30`, `:35`, `:43`). Those are different lifetimes. Existing source triggers intentionally invalidate unused proofs on status, suspension and membership changes (`20261022180000_diagnostic_public_continuity/migration.sql:82`). They must remain, but are not a ready-made permanent ownership predicate.

Literal overblock: same Listing/seller/commissioner/member, Business temporarily suspended then restored, with no transfer or identity change. A new automatic proof would be refused forever under a broad sticky eligibility bit even though current authority is restored. Likewise owner/sales role changes do not themselves change publisher admission: `apps/api/src/modules/identity/domain/PublisherParticipant.ts:7` checks active matching membership/business, not role. Pause/relist is already correctly excluded by the handoff. Apply the same separation consistently to User/Business status, staff/session/assignment, appointment and unrelated evidence changes.

Required correction: enumerate the irreversible ownership/identity predicates separately from current eligibility and existing unused-proof invalidation. Actual seller, Listing identity/id, commissioner, business association and required membership replacement/revoke/restore history must not be hidden by restoration. Do not assume every role/status change means ownership changed. Any additional permanent refusal without such a change is a new product decision, not a routine trigger choice. Retain current distinct pair-assigned reviewer authority without settling broader automatic issuers.

### P1. Historical third-party erasure needs a separate component state and lock discovery

The handoff identifies this correctly but leaves it as a likely exception. Current purge finds commissioner-owned orders/reports and staff attribution, not historical seller ownership facts (`apps/worker/src/jobs/diagnosticAccountErasure.ts:9`, `:23`, `:66`). It starts with only the deleting User lock, does diagnostic erasure, then deletes membership later (`apps/worker/src/jobs/PurgeExpiredAccounts.ts:61`, `:136`). Extending this transaction with historical-fact writes without reconciling the same lock prefix is unsafe.

Literal leak: staff records visit for commissioner C on a Business Listing whose recorded seller is S; Listing later names S2; S is purged. A fact containing S, its digest and a proof copy survives if cleanup searches only C or current Listing seller S2. Whole-raw erasure is also wrong: it would remove another commissioner's vehicle evidence and invalidate raw report pins unnecessarily. The raw erasure state currently clears observation/hash together (`20261021110000_diagnostic_identity_records/migration.sql:15`, `:31`); it cannot represent ownership-only redaction.

Required correction: immutable ownership-content state with explicit unavailable/erased representation, allowing only irreversible component redaction while leaving raw observation and report pin intact. Discover references through retained raw facts and proof bindings, including replaced membership owners, before membership rows disappear. Fence future automatic admission permanently, clear personal digests as well as IDs, and remove affected restricted proof copies, including consumed copies when their personal content must be erased. Preserve B's report-level retry binding and ordinary updates/release. Consumed links survive later A changes by ADR-0108:45; `PrismaDiagnosticReports.ts:243` retries from the report's stored proof id/order version, without requiring the proof payload. Do not keep a hash as an erasure substitute.

### P2. Fact capture and SQL authority must be specified beyond adding nullable JSON

Observation currently locks participants, checks authorization/VIN and writes the latest Listing digest, then appends raw observation (`PrismaDiagnosticIntake.ts:212`). It does not call the current publisher bind as an observation admission rule. Capture historical ownership from those locked persisted rows, including a foreign seller and applicable membership, without introducing a new requirement that observation itself already has B's future publisher authority. Missing/ineligible original authority can make automatic unavailable without denying an otherwise authorized observation.

The raw INSERT guard presently authenticates only order/version/current observation (`20261021110000_diagnostic_identity_records/migration.sql:31`); simply extending its immutable UPDATE comparison would freeze forged INSERT content. Bind new content to persisted source rows and the witness at INSERT, under the same serialization as observation. Separate genuine personal `businessId=null`/no membership from missing JSON keys, invalid business membership, legacy absence and erasure. Protect initial anchors, witness initialization, increments and false/zero resets. Checking monotonicity alone permits fabricated initialization or increments that overblock valid visits.

Use predicates returning an explicit boolean, reject when the result IS NOT TRUE. PostgreSQL CHECK and PL/pgSQL IF do not reject UNKNOWN by themselves. The existing proof guard uses `OR NOT diagnostic_continuity_proof_bound(NEW)` (`20261021160000_diagnostic_automatic_vin_proof/migration.sql:5`); a newly nullable ownership helper must not turn this into a bypass. Use the same ownership predicate at issue, consume and report INSERT, preserving atomic audit/report checks. Do not add automatic-only historical requirements to comparative or private admission.

### P2. Transition coverage must follow original facts, not current association or proof existence

The handoff's central diagnosis is correct. The association trigger only updates nonnull associations and records no reason/history (`20261015280000_diagnostic_association_invalidation/migration.sql:6`). Current proof invalidation sees only issued unused proofs, and membership matching is B-publisher-only (`20261022180000_diagnostic_public_continuity/migration.sql:93`). Neither is an ownership-history mechanism.

Literal bypass without the new witness: A observed/released under S1; S1 → S2 → S1 with no intervening observation; authorized reobservation restores the original digest; B observes S1. All retained owner tuples could be equal. Requiring tuple equality alone admits this. The current restore test follows this history but refuses at the blanket domain gate, not historical discrimination (`apps/api/src/modules/diagnostics/presentation/DiagnosticPublicTransferProof.e2e.spec.ts:851`, `:878`). Watch finalized A and null-associated visits before any proof, with OLD and NEW membership targets and original fact references. Commissioner/Listing reassociation, if writable, needs equivalent coverage or an explicit immutability guard. Reobservation must never establish a new first anchor after a missing/erased earlier one.

## Smallest coherent contract and data scope

The simpler option is a database-owned irreversible visit-local bit, initialized only with the first complete forward fact, plus restricted per-raw ownership binding. A visit-local generation is equally valid if every raw capture binds its generation and it is compared to that visit's original/live generation. Never compare A's generation number to B's. Generation adds useful complexity only if something consumes distinct transitions. A global source generation vector or ledger is unnecessary. Reusing order version, evidence generation, timestamps, association-null state or the repeatable publisher digest cannot distinguish lawful reobservation from ownership restore (`PrismaPublisherBindings.ts:35`; `PrismaDiagnosticContinuityProofs.ts:86`). Merely refusing all reobservations is a smaller implementation but an unauthorized overblock. This comparison is a review recommendation, not architecture selection.

Retain enough restricted information to compare the original Listing identity/ownership and find every personal subject for erasure: Listing reference, normalized identity binding, seller subject, commissioner subject, nullable Business and the applicable membership binding. The membership can use the recorded commissioner as its subject; another duplicate member-user id is unnecessary. Raw id/order/version and report pins already supply record ownership/time anchoring. A duplicate commissioner id can be avoided only if its order binding is proven immutable except erasure; do not infer that from today's API. A separate full-tuple hash is optional when canonical content is bound directly. The existing Listing digest already includes Listing/seller/Business/normalized VIN/brand/model/year (`diagnosticListingDigest.ts:2`); storing another equivalent digest or all those identity values again buys no history. Keep required searchable subject references rather than retaining opaque hashes that cannot support erasure discovery. All such IDs/digests remain identifying data. No names, contact details, former-owner narrative or public snapshot fields are needed.

Keep vehicle observationHash v1 and report pins unchanged. First drafts select raw pins; same-visit corrections inherit them, including missing legacy pins (`PrismaDiagnosticReports.ts:63`; `20261021120000_diagnostic_report_identity_pin/migration.sql:13`). New restricted fact fields can live beside that pinned raw. Inspect all raw histories, the original A pin and B current record; missing/erased facts refuse automatic, while supported comparative corrections retain their existing complete graph rules. Do not repin an old report or fabricate legacy facts. Disposable prelaunch data needs no preservation/backfill infrastructure, but product behavior after launch still needs the erasure and concurrency contract above.

Existing classified-data policy can own the new component; it grants no indefinite personal retention (`docs/prd/features/50-reports-tier.md:145`; ADR-0108:51). Explicitly identify its existing permitted purpose/rights and deletion owner. Proof copies expire at the shortest retained evidence/provenance right (`apps/worker/src/jobs/diagnostics/DiagnosticArtifactWorker.ts:156`). That worker currently expires structured evidence/proofs, not raw ownership content. Attaching the new fact to raw does not automatically supply a lawful rights schedule. If governed by rights-limited material, erase its component and derived copies when those rights end or earlier applicable subject erasure requires it. A purpose still legitimately needed under existing rights may retain the minimum permitted component, never on the theory that a hash is anonymous. If no applicable existing deletion treatment can be identified, that mapping remains unresolved; reject permanent retention rather than inventing a TTL or hold power. No new retention system is required merely to implement an existing deletion rule.
