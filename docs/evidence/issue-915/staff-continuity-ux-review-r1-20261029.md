Findings

F1. Severity 3, blocking. The capture/correction design does not constrain the editable target and supporting material to the current append contract.

The wireframe's ASCII correction block says to select a retained record to correct. Lines 112 and 118 describe immutable history, a visible server-record selector and complete corrected identifiers, rights and explanation. The append binding at line 133 uses the selected raw record. It does not say that historical raw records are read-only targets, that a superseded structured record cannot be corrected again, or that a correction must introduce at least one provenance reference unused by earlier evidence.

The distinction matters after a recording history or correction chain exists. A technician can reasonably select the original displayed record, enter a complete correction and select already verified supporting images. Those choices look valid under the written flow, but the actual endpoint refuses them. Re-entering the same values does not repair the problem, and its public refusal cannot explain which hidden source condition failed.

Governing source at base `0617c7d` is `apps/api/src/modules/diagnostics/infrastructure/PrismaDiagnosticIdentityEvidence.ts:299-316`:

- The bound raw record must be the current unerased raw observation, checked at lines 302-305.
- A new root is permitted only where that raw record has no structured evidence, at lines 306-307.
- A correction's retained parent must have no successor and remain usable, at lines 309-313.
- At least one submitted provenance ID must be absent from the references used by earlier records, at lines 314-316.

The strict capture schema at `packages/contracts/src/schemas/diagnostics.ts:63-73` alone does not express these backend preconditions. The action forwards the supplied capture through that schema at `apps/admin/src/app/diagnostics/actions.ts:53-54`. `diagnosticFailure` sanitizes protected refusals in `apps/admin/src/lib/diagnostic-transport.ts:20-24`. This is a source-contract gap in the state design, not an assertion that production UI has been implemented incorrectly.

Minimal fix: specify a separate read-only history and an eligible capture target. Bind new evidence to the current raw observation from fresh server history. Offer a new root only if it has no structured evidence; offer correction only for the retained unsuperseded leaf. Show the original pin and full chain for orientation without making historical rows arbitrary write targets. Explain and require at least one newly staged/verified supporting image not used in earlier evidence, while allowing existing references alongside it. After stale/denied refresh, recompute eligibility and require review before submission. Use the existing records/evidence responses and endpoints, with the server still authoritative. Do not add a root-selection policy, grant or endpoint. Preserve generic refusal for facts the actor is not allowed to inspect.

Heuristics affected: error prevention, recognition rather than recall, constraints, and actionable recovery. Frequency is conditional on retained history or correction work; impact is a failed core task, and it persists across identical retries. Resolve in the wireframe and contract table before hi-fi so the next owner is not forced to invent the state behavior.

F2. Severity 2, nonblocking refinement. Pair-image failure disables issuance, but the keyboard recovery destination is underspecified.

Wireframe lines 183-187 specify useful success, comparison and denial focus behavior. Image failure hides bytes and unarms issuance, while the general error row covers an inline alert and field link. It does not give a precise comparison-image retry/back control or focus fallback if the failed preview or issuance control disappears. Stale/conflict recovery similarly names actions without identifying where focus goes after the protected comparison is removed.

Minimal fix during hi-fi: place a labeled Retry protected image or Reload comparison control next to the failed image status. Retain focus on the invoking control where it survives; otherwise focus the comparison error heading, then expose retry and Back to candidates in reading order. Revoke failed previews, keep issuance unavailable, and require the complete pair/support review again. A 401/403 follows denial clearing and safe navigation, rather than image retry with cached material. Do not automatically issue after recovery. This extends the existing native-control/status model and needs no new route or permission.

Governing evidence: wireframe state and accessibility sections; the exact-pair proxy in `apps/admin/src/lib/diagnostic-identity-files.ts:23-43`; reauthorization after storage I/O in `PrismaDiagnosticIdentityEvidence.ts:202-215`. The eventual focus and live-region behavior requires rendered keyboard proof. The missing named focus destination is a bounded design refinement, not evidence of a rendered keyboard failure.

Answers to all seven independent questions

1. Ordinary report, editorial correction and new linked visit: adequate design distinction. The three choices have separate placement, commands and outcomes. Start empty report creates an unlinked B draft; editorial correction preserves the same visit's original observation; linked reinspection opens B's first report with B's own date, mileage, template and empty findings. An already authored ordinary draft is not converted. The no-inheritance notice appears before linking. This agrees with ADR-0104/0108 and the existing draft/correction/reinspection contracts. Keep the eventual copy explicit that the identity-record correction in F1 is also distinct from an editorial report correction. Existing make/model/year finalization inputs and immutable release identity remain required, as seen in `DiagnosticWorkspace.tsx:35-37,47,54-56` and contracts lines 106-117. No replacement VIN-only release identity is proposed.

2. Rights before bytes and immutable pins: upload ordering and comparison display are adequate, subject to F1 and F3 for capture. Rights start blank, including an explicit authorized end. The picker remains unavailable until rights are complete; staging precedes PUT; only verified sanitized results can be referenced. Fixed service-only/staff-only/no-hold constraints do not invent rights. Rights for physical evidence are not authenticated ownership grants. Original observations and corrected values remain visible through explicit edges; later raw records do not silently repin a report. The comparison projection returns the pinned evidence plus its explicit corrections, not a client-selected newest root. Corrections must additionally obey the source capture eligibility in F1. Later real-source rights and protected-storage acceptance remain outstanding.

3. Traversal, full comparison and named technician: adequate design binding. Predecessors use their own B/actor/session-scoped cursor action, independently of the old assigned queue cap. Zero candidates with a cursor keeps Continue search visible; exhaustion describes the authorized retained scope only. A candidate displays only report reference, date and mileage. Comparison loads the exact full pair and uses only its versions, raw record IDs/hashes, pinned material and corrections. The design explicitly derives the deduplicated union of every provenance ID in both returned evidence records and their corrections, freezes deterministic ordering, and refuses oversize/insufficient input rather than pruning it. `PrismaDiagnosticReports.ts:190-193` builds the pair provenance union; `PrismaDiagnosticContinuityProofs.ts:115-123` requires exact set equality; the issuance schema limits it to 40 IDs. A checkbox cannot turn a subset or equal identifier text into proof. The B technician selector uses the current eligible-name action, not reception staff choices, arbitrary UUID entry or a general directory. Server admission remains final for both methods, including automatic normalized-VIN requests.

4. Historical issuance versus usable handoff: adequate design distinction. Preparation stores only request identity. Issuance creates no B report and returns a historical handle, including after reload. Only current B handoff admission supplies usable status and expected order version. A full proof read remains dual-authorized and does not certify current use. The design preserves the independent dual-assigned reviewer, independence from A's author/reviewer and B's technician, and current issuer/session/qualification checks. ADR-0109 ownership grants, publisher eligibility, fresh public consent and association remain separate. Equal VIN, physical access and image rights grant none of these powers. Multiple-root and broader automatic-issuer frontiers are not silently resolved by this wireframe.

5. B-only consumption/reload: adequate design disclosure boundary. Handoffs expose only opaque proofId, usable status and B version; completion exposes proofId/reportId. Local ordinal labels do not invent A identity, chronology or preference. The wireframe excludes A details, reviewer rationale, provenance and hashes from visible content, DOM/accessibility labels, toasts, persistence and telemetry. Consumption adds only B's report ID and reason to the current handoff binding. A completed consumption opens the authorized B report directly. `PrismaDiagnosticContinuityProofs.ts:331-355,694-698` supports B-owned completion/result recovery without A or proof-content reads; `useHandoffIn:738-753` recognizes existing B results without repeating mutable A admission. The instruction not to display A details from `successorOf` must cover the existing workspace history output at `DiagnosticWorkspace.tsx:46`. That is an explicit design requirement, not permission to keep the generic history label for B-only users. Current B authority remains necessary.

6. Pending, ambiguous and lost replies: adequate under the coordinator ruling. Same-page memory holds the exact submitted command, including report ID, versions, method/reason and ordered provenance. An ambiguous execute first triggers explicit GET recovery. Completed consumption opens B; completed issuance remains historical. Pending permits explicit exact retry only while that exact command survives in memory and authority permits it. Reload discovery recovers the same request identity, not lost form input or a former candidate. The pending notice explicitly says input was not saved, then requires fresh re-entry/review under the same requestId. If an older execute commits after pending GET, the changed command may conflict; the design surfaces conflict and recovers the result without hidden reprepare or mutation replay. Lost prepare replies require paginated discovery first; multiple pending handles remain explicit choices without fabricated metadata. Contracts lines 203-215 and `prepareRequest:303-315`, `sameIssuance:288-295`, `executeRequest:404-459` support these distinctions. No protected browser command store, automatic replay, replacement request or claim of recovered original command is allowed. An unavailable old Session is not silently adopted by a new sign-in.

7. Keyboard/focus/status/error/recovery, tablet and locales: mostly adequate written coverage, with F2 remaining. Native controls, visible labels, fieldset/legend, associated validation, polite progress/success, blocking alerts, no hover-only meaning and no textarea Enter-to-issue behavior are specified. TK/RU/EN must cover all new labels/help/alt/errors/status/recovery text; English wireframe placeholders are not accepted translations. Dates remain UTC and canonical values are not reparsed on language switch. Actual contrast, target areas including checkbox labels and language control, 200% zoom, text expansion, focus and screen-reader announcements need later rendered proof.
